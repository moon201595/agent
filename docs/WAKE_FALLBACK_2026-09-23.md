- **10:12:12 KST 확인 시 아직 10:30 전**이다. `logs/cron.log`는 17줄, 마지막 `:17`은 `정상: 2026-09-22 KST 브리핑 종료·저장·발송 확인`. 오늘 10:30 실제 감시 실행/출력은 미실측이다. 미래 회차를 확인했다고 쓰지 않는다.
- 위 명령으로 오늘 실제 시작 로그에 `_late_start`만 호출했다. 출력은 **`오늘 스캔이 예정(05:00)보다 4.8시간 늦게 시작했다 (실제 09:49 KST) — PC 가 제때 안 깨어났을 수 있다`**. `LATE_AFTER=2시간`, 2시간 이상이면 표시한다(`scripts/check_daily_mail.py:58-82`). 로그 시작점 판정은 정상이다. 이는 **함수 출력**이며 `cron.log`에 오늘 기록된 출력은 아니다.
- 중요한 조건: 감시 main은 락이 잡혀 있으면 `_late_start`보다 먼저 보류/exit 0한다(`:220-222`). 완료·저장·발송 검사에 문제가 없어야 지연 문구를 찍고 exit 0한다(`:238-254`). **지연 알림 메일을 보내는 기능은 아니다.** 문제가 있으면 기존 문제 경로로 간다(`:256-275`). 10:30에도 스캔 중이면 지연을 표시하지 않고 보류한다. 알려진 두 회차뿐이라면 같은 날 후속 감시 회차가 없어질 수 있다. 정시 05:00 시작 후 처리가 길어진 날도 `_late_start`는 잡지 않는다(첫 시작만 판정).
- `check_daily_mail.py --dry-run`도 실행하지 않았다. main에는 락 파일 append-open(`:37`)과 일반 SQLite 연결(`:146`)이 있어 이번 “문서 외 쓰기 금지·DB mode=ro” 검증에 맞지 않는다. 순수 함수 호출만 했다.

### 05:00 운영일 경계

`time_policy.py:68-76`에서 운영일은 KST 05:00부터다. 9/23 09:49는 9/23 운영일이고 경계는 **9/22 20:00 UTC**다. 감시는 local date로 경계를 구하고(`check_daily_mail.py:85-88`), 그 뒤 시작/종료를 고른다(`:178-184`). 09:49 실행은 정상적으로 이 구간에 포함된다. 메일 제목도 KST 오늘 날짜(`scan_deliver.py:49-53`), DB digest 날짜 비교도 KST(`check_daily_mail.py:139-165`)이므로 **이번 09:49 때문에 날짜가 어제로 밀리는 문제는 확인하지 못했다.**

다만 감시의 `_operational_day`는 `time_policy.operating_day`를 직접 쓰지 않아 05:00 이전에는 서로 다른 날짜를 고를 수 있다. 새 매시 감시/따라잡기를 추가할 때 00:00~04:59를 제한하거나 정책을 통일해야 한다. 현재 06:30·10:30 및 09:49에는 이 차이가 발현하지 않는다. 자정/다음 운영일까지 넘어가는 장기 실행은 별도 경계 사례이며 이번 실측 대상이 아니다.

**실제 손상은 아침에 읽어야 할 브리핑의 부재와 감시 공백이다.** 05:00는 발송 완료 목표가 아니라 기동 예정시각이므로, 시작 지연과 처리시간을 구분해야 한다. 9/22는 09:53:41에 시작해 10:26:01에 끝났다(`daily_scan.log:3945,4204`); 오늘은 09:49:45 시작 뒤 S2·LLM 재시도까지 겹쳤다. 늦은 시각 때문에 API 장애가 발생했다는 인과관계는 미확인이다. 검색 시각이 바뀌면 후보 집합·순위도 달라질 수 있지만 그 차이·손실량은 미실측이다.

### (a)를 한 줄로 추가하면 안 되는 이유

`run_daily_scan.sh:39-43`의 flock은 겹치는 실행만 막는다. 같은 날 한 번 완료했다는 검사는 `:54-82`에 없다. `run_profile_scan.py:549-559`는 호출될 때마다 daily 프로필을 스캔하고 발송한다. `scan_deliver.py:82,90-106`도 새 회차를 만들고 수신자마다 전송하며, 0편이어도 보내는 경로다. 따라서 “락이 없으면 실행”은 “오늘 미실행이면 실행”이 아니다. 기존 논문이 shown으로 빠져도 새 메일 자체는 나갈 수 있다.

안전하게 도입하려면 **같은 daily flock 안에서** 오늘 상태를 다시 확인하고 실제 작업으로 넘어가야 한다. 바깥 조회 뒤 별도 셸을 띄우면 조회와 실행 사이에 Windows 실행이 끝날 수 있다. 이미 잡은 flock을 다른 자식 셸이 다시 획득하게 만들면 자기 스킵/대기도 생길 수 있어 진입점 계약부터 정해야 한다. 미실행의 뜻도 먼저 분리해야 한다.

- **기동 누락만 보충**: 오늘 시작/시도 기록이 없을 때만 실행. 부분 발송 재전송 위험이 작지만 시작 직후 죽은 회차는 자동 복구하지 못한다.
- **실패 회차 재시도까지**: scan_runs만으로는 발송 성공을 알 수 없다. profiles.last_digest_at도 발송 보장이 아니다. 수신자별 성공/부분 실패를 보존하고 이미 받은 사람에게 재전송하지 않는 정책이 필요하다. SMTP 수락 직후 기록 전에 죽는 경계까지 정확히 한 번 보장은 별도 문제다. 단순 일자 stamp나 마지막 exit 0만으로 해결하지 않는다.
- 주말·공휴일, 05:00 전, manual 프로필, 다음 운영일로 넘어간 실행, 검색 저하인데 메일은 발송된 exit 2도 다뤄야 한다(`run_profile_scan.py:594-620`). 실패할 때마다 매시간 비싼 작업을 반복하지 않도록 재시도 범위/백오프가 필요하다.
- 주간일에 재호출하면 일일 셸이 주간 stamp를 읽지 않아 db_retention을 다시 부른다(`run_daily_scan.sh:75-79`). 수동 주간 스크립트에는 있는 stamp 검사(`run_weekly_agent.sh:28-31`)가 여기에는 없다. `agent_maintenance` 자체의 예약 가드와 DB 정리 반복 문제는 다르다.

관련 근거 조회 명령: `nl -ba run_daily_scan.sh`, `nl -ba run_weekly_agent.sh`, `nl -ba run_profile_scan.py`(531~620), `nl -ba scan_deliver.py`(56~125), `nl -ba agent_maintenance.py`(733~739). 출력에서 위 조건·호출 순서를 직접 확인했다. 재실행/중복 발송 실험은 **미실측**이다.

### (b)의 구체적인 기록안

기존 `=== ... 시작 (pid ...) ===` 줄을 그대로 두고 **별도 메타데이터 줄**을 추가하는 편이 안전하다. `scripts/check_daily_mail.py:46-47`은 줄 끝까지 고정된 정규식이며 `scripts/morning_report.py:30-53`도 이 형식으로 블록을 찾는다. 시작 줄 괄호 안에 source를 넣는 식의 변경은 파서를 깨뜨린다.

기록 후보는 명시적 source(cron/windows/manual/unknown), PID·PPID, 실제 UTC/KST 시각, 예정 운영일·05:00, 지연 초, DAY_KIND, 락 획득/스킵 결과다. source가 전달되지 않았으면 **unknown**으로 남겨야 한다. Windows라는 단정은 명시적 호출자 표식 없이 하지 않는다. 전체 환경변수나 부모 전체 인자를 덤프하지 않고 허용된 필드만 기록한다. 수동·휴일·05:00 이전 실행에는 “예정 시각 없음/해당 없음”을 구분해 잘못된 음수 지연을 만들지 않는다. flock 스킵 전에도 호출 시도 메타데이터가 있으면 어느 두 경로가 충돌했는지 알 수 있다.

Windows 작업에서 source를 전달하는 변경은 사용자 동시 작업 영역이다. 이번 범위에서는 바꾸지 않는다. 향후 저장소만 수정한다면 표식 없는 기존 호출은 unknown으로 남는 한계를 수용해야 한다.

### (c)가 이미 동작한 것인가

**9/22는 그렇다: 저장소의 과거 조사 기록 기준이다.** `PROGRESS.md:6771-6782`가 사람 복귀·StartWhenAvailable 이벤트·실행을 연결하고, 실제 daily_scan.log의 시작/스킵이 부합한다. 그날의 두 번째 WSL cron을 덧붙여도 잠든 동안의 지연을 해결하지 못하며 복귀 직후 Windows 실행보다 빠르게 시작한다는 근거도 없다. **9/23에도 (c)가 작동했다고 확정할 자료는 없다.** 따라서 “현재가 모든 상황에서 최선”이라고 확정하지 않고, “기존 따라잡기는 유지할 근거가 있으며 관측 보강이 우선”으로 판단한다.

### (e)의 최소 범위

기존 `run_daily_scan.sh:82-94`는 종료코드를 기록한 뒤 morning_report를 만든다. 이 경로에 순수 로그 분석 결과(시작 지연, 실제 소요시간, 완료/저하)를 붙이는 방식이면 스캔 추가 없이 감시 보류 공백 일부를 메운다. 진행 중인 10:30 감시에서도 시작 지연 사실과 아직 완료되지 않았다는 상태를 함께 출력하는 보강을 검토할 수 있다.

기존 감시 main을 그대로 스크립트 끝에서 호출하는 것은 권하지 않는다. `exec 9>`로 연 FD는 중괄호가 끝났다는 이유만으로 닫히지 않으며 셸에 명시적 `flock -u`/`exec 9>&-`가 없다(`run_daily_scan.sh:39,85-103`). 감시의 락 검사에 걸려 다시 보류할 수 있다. 완료 로깅을 순수 파서로 수행하거나 락 수명과 상태 재확인 순서를 설계해야 한다. 실제 FD 수명 재현은 이번에 하지 않았으므로 실행 실측이 아닌 셸 코드 검토 결과다. 완료 후 “지연”을 남기는 것은 관측 개선이며 05:00 깨우기 문제의 해결은 아니다.
