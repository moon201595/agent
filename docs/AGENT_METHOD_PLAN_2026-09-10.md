# 연구 브리핑 에이전트 방법론 구현·평가 계획

작성일: 2026-09-10. 상태: 설계 제안, 구현 승인 전. 이번 작업은 이 계획서 작성이며 운영 코드·DB·메일은 변경하지 않는다. 아래 새 파일명·플래그·테이블·실험 규모는 모두 제안이다. 기존 기록과 계획 수치를 구분한다.

## 1. 결정할 방향

목표는 관심 연구축의 새 논문을 찾아, 근거와 코드 실행 상태를 구분한 브리핑을 제한된 자원 안에서 완성하는 것이다. 제안 방법은 **근거 결손에 반응하는 제한된 행동 선택 에이전트**다. LLM이 공개 자료에서 추가 확인할 대상을 고르고, 코드는 도구의 실행 조건과 완료 판정을 소유한다.

첫 버전은 단일 에이전트다. 기존 run_daily_scan.sh → run_profile_scan.scan_and_digest → batch_summarize._process_paper → _deliver 경로를 확장한다. 별도 상위 실행기·LangGraph·Airflow·멀티에이전트를 도입하지 않는다. cron은 기동 시점을, 에이전트 정책은 실행 중 다음 확인 대상을 정한다. Raspberry Pi 배치는 후속 운영 검증이다.

논문 후보 제목: **근거 결손에 따라 도구 사용을 조정하는 연구 모니터링 에이전트의 설계 및 평가**.
특허 검토 후보: **연구 관찰의 근거 의존관계와 실행 제약에 기반한 에이전트 행동 선택 방법**.
등록 가능성·품질 개선 효과는 아직 확인하지 않았다.

## 3. 구현 후 한 번의 실행 예시

아래는 동작 설명용 가상 사례이며 실제 논문 분석 결과가 아니다.

1. 최초 검색과 선별은 현재 경로로 수행한다. 개인화 점수와 미처리 후보를 준비한다.
2. 공개 제목·초록을 보고 LLM이 이번 브리핑에서 확인할 관찰 후보와 관련 논문 ID를 제안한다. 이는 가설이며 확인된 사실이 아니다.
3. 코드가 현재 가능한 후보 행동만 만든다. 이미 처리한 대상, 대기 중인 소스, 남은 시간에 맞지 않는 작업을 제외한다.
4. LLM이 후보 중 다음 논문을 고른다. 예: 다른 논문과 중복되는 상위 후보 대신 아직 본문을 읽지 않은 연구축의 논문을 선택한다.
5. 기존 _process_paper가 본문 확보·요약·검증·재현 시작을 수행한다. 실제 반환 결과로 상태를 갱신한다.
6. 확보한 공개 원문이 기존 관찰의 범위를 좁힐 필요를 보여주면 LLM은 관찰 후보를 수정하거나 다른 논문 확인을 제안한다. 코드상의 검증 성공 상태는 LLM이 바꾸지 못한다.
7. 남은 작업과 자원을 다시 계산한다. 최초 실행과 다른 다음 행동을 선택할 수 있어야 한다.
8. 완료 또는 마감 시 현재 상태를 고정하고 동향 → 논문 순서로 메일을 생성한다. 재현 미완료 사유는 해당 논문 안에 적는다. 다음 메일의 과거 상태 소식은 만들지 않는다.

## 4. 상태 모델: 근거를 한 숫자로 합치지 않는다

### 논문 상태

paper_key는 기존 합성 ID·DOI 등 식별 규칙을 재사용한다. 메타데이터만 있음, 초록 있음, 본문 확보, 요약 있음, 재현 진행 등은 독립 필드다. 초록만 있다는 이유로 목록에서 사라지지 않는다.

### 관찰 후보

observation_id, 후보 문장, 관련 공개 논문 ID, 관련 관심 키워드, evidence_refs를 둔다. LLM이 생성한 연결에는 origin=model_proposed를 붙인다. 확인할 대상의 선정과 내용의 진위 판정을 혼동하지 않는다. 분야 전체의 증가·감소를 말하려면 기간·검색 범위 비교가 별도로 필요하다.

### 근거 상태

본문 확보 범위, 원문 위치 식별 가능 여부, 수치 대조 결과, 코드 설치·실행 결과, 논문 결과 수치 대조 여부를 별도로 기록한다. 예컨대 수치 불일치는 본문 전체가 거짓이라는 뜻이 아니고, Docker exit 0은 논문 성능 재현이 아니다. contradiction 같은 의미 판정을 LLM 응답만으로 확정 상태에 저장하지 않는다. 모델은 possible_conflict라는 검토 후보만 제안할 수 있다.

### 실행 상태와 이력

run_id, action_id, paper_key, 상태, 시도 번호, 시작·종료, 결과 코드, 입력 버전, 정책·프롬프트 버전, 다음 재시도 가능 시각을 기록한다. 상태는 pending/running/succeeded/failed/blocked/deferred로 구분한다. blocked는 GPU 부재 등 확인한 선행 조건 부족이고, timeout은 실패 원인 또는 미완료 사유이지 실행이 실제 종료됐다는 뜻이 아니다.

추가 저장은 별도 additive 테이블 agent_runs, agent_actions, agent_observations를 후보로 한다. 기존 evidence_state와 중복되는 필드는 재사용한다. 전체 자료를 복제하지 않고 ID·버전·결과 참조를 저장한다. DB 변경은 구현 단계의 별도 검토 대상이다.

## 5. LLM 정책과 실행 제어의 경계

LLM의 역할은 다음 확인 대상과 공개 근거에 기반한 짧은 선택 이유를 제안하는 것이다. 숨은 사고 과정을 저장하도록 요구하지 않는다. 코드는 후보 행동 생성, 권한, 예산, 선행 조건, 멱등성, 도구 호출, 상태 갱신, 성공 판정을 맡는다.

LLM 출력 계약 예시:

```json
{
  "action_id": "candidate-17",
  "observation_ids": ["obs-3"],
  "evidence_refs": ["paper-A:abstract"],
  "reason_code": "missing_full_text",
  "rationale": "이 관찰의 근거 논문은 아직 초록만 제공됐다."
}
```

action_id는 코드가 발급한 허용 목록에 반드시 있어야 한다. 임의 함수명·셸·URL·파일 경로·SQL을 실행하지 않는다. evidence_refs는 실제 제공한 자료를 가리켜야 한다. 일치해도 의미 지지로 인정하지 않는다. 허용되지 않은 선택, 형식 오류, 모델 시간 초과에는 결정적 정책으로 즉시 폴백한다. 포맷 수정을 위한 무한 LLM 재질의는 하지 않는다.

### 외부 전송 제한

Gemini 무료 우선·Groq 대체를 유지한다. 외부에는 공개 논문 텍스트·서지와 허용된 관심 키워드만 보낸다. 사내 계획, 사용자 피드백 원문, 수신자, DB 경로, API 키, 원시 실행 로그, 내부 성과 수치는 보내지 않는다. 시간·자원·API 장애·실패 상세는 로컬 실행 제어에서 처리한다. 외부 제안기는 로컬에서 거른 후보와 공개 근거를 받으며 내부 상태의 이유를 별도 설명받지 않는다. 후보 ID는 불투명한 실행 내 식별자다. 공개 자료로부터 만든 설명도 외부 전송 전 허용 필드 투영을 거친다.

이 제한 때문에 초기 LLM은 API 오류 자체를 해석하지 않는다. 로컬 정책이 실패한 행동을 제외하고 남은 선택지를 모델에 제공한다. 운영 상태까지 모델에 보내는 설계는 현 규칙 4를 넓혀 해석하지 않고 별도 정책 검토로 남긴다.

## 6. 행동 공간: 한 번에 세부 단계까지 분해하지 않는다

| 행동 | 첫 버전 | 후속 버전 / 제한 |
|---|---|---|
| PROCESS_PAPER | 허용 후보에서 다음 논문을 선택해 기존 _process_paper 호출 | 가장 먼저 구현한다 |
| FINALIZE | 로컬 종료 조건 충족 시 고정된 결과로 브리핑 생성 | LLM이 마감을 연장하거나 발송 성공을 선언하지 못한다 |
| WAIT_FOR_EXISTING | 이미 시작된 작업을 제한 시간 내 관측 | 새 재현 시작이나 무한 기다림을 뜻하지 않는다 |
| SEARCH_SUPPLEMENT | 첫 버전 제외 | 기존 델타 커서를 움직이지 않는 추가 검색으로 별도 설계한다 |
| FETCH_ALTERNATIVE | 첫 버전은 기존 함수 내부 폴백만 사용 | 실행 단계를 분리한 뒤 허용 출처에 한해 노출한다 |
| CHECK_NUMERIC_EVIDENCE | 기존 save_summary 검증을 재사용 | 입력 변경 없이 같은 검사 반복은 금지한다 |
| RETRY_REPRODUCTION | 첫 버전 제외 | 기존 Docker 내부 재시도만 유지한다. 새 자동 트리거 금지 |

추가 검색 결과는 출처·질의·관측 시점을 별도로 남기고 정규 델타 검색 완료나 분야 전체 포괄로 계산하지 않는다. 서술의 한 문장을 뒷받침하려고 같은 질의를 반복하는 확인 편향도 평가한다.

첫 버전이 증명할 것은 논문 단위의 적응형 선택이다. 원문 표·문장 단위 검증 스케줄링까지 구현했다고 주장하지 않는다. 후속 버전에서 _process_paper 내부를 재사용 가능한 단위로 분해하려면 기존 자동 전이 소유를 보존하는 별도 설계가 필요하다.

## 7. 다음 행동을 고르는 방법론

초기 결정적 기준선은 순서가 명확한 규칙으로 만든다: 실행 가능성 → 중요한 관찰의 부족한 근거 → 아직 다루지 않은 연구축 → 중복 감소 → 기존 관련도 → 안정적인 ID 순서. 정책 점수는 진실 확률이 아니다.

제안 에이전트는 이 후보 집합에서 공개 근거를 읽고 다음 행동을 고른다. 선택 후 실제 결과를 반영해 후보를 다시 만든다. 관찰과 근거 연결은 매 단계 버전이 바뀌며, 이미 처리한 근거를 다시 새 기여로 세지 않는다.

후속 연구에서는 행동 a의 우선순위를 ‘관련 관찰들의 미충족 근거에 대한 예상 기여 / 실행 비용’으로 정량화할 수 있다. 단, 예상 소요 시간·완료 가능성에 충분한 과거 표본이 없으면 unknown으로 두고 보수적인 한도를 쓴다. 모델이 낸 숫자를 성공 확률로 사용하지 않는다. 공통 근거를 쓰는 관찰 여러 개를 중복 합산해 과대평가하지 않도록 고유 관찰·근거 집합을 사용한다. 여러 논문을 함께 읽어야 확인할 수 있는 관찰은 한 논문만 읽었다고 충족 처리하지 않는다.

모든 관찰을 하나의 신뢰도 점수로 합치기보다, 근거 유형별 미충족 집합을 유지한다. 특허 검토의 핵심 후보도 이 집합과 실제 실행 결과가 다음 행동 선택을 바꾸는 구체적 관계다.

## 8. 시간·자원·재시작 정책

### 마감

논문별 재현 확인 상한 3,600초는 기존 사용자 요구로 유지한다. 별도로 digest_deadline과 finalization_reserve를 둔다. 정확한 아침 발송 시각과 전체 예산은 운영 전 확정할 설정이며 이번 계획에서 임의로 확정하지 않는다. 논문별 유효 대기 시간은 원래 상한과 남은 전체 작업 시간 중 짧은 값이다. 전체 마감으로 먼저 멈춘 경우 ‘1시간 재현 실패’라고 쓰지 않고 ‘메일 마감 도달, 실제 대기 시간’으로 표시한다.

최초 프로세스 시작부터 검색·요약·정책 호출·재현 관측을 모두 전체 경과 시간에 포함한다. 이미 시작된 요청에도 남은 시간에 맞는 timeout을 전파해야 한다. asyncio 취소가 스레드나 Docker 프로세스를 종료한다는 가정을 하지 않는다. 완료 처리에 필요한 여유를 따로 남기고, LLM이 응답하지 않으면 기존 요약 기반의 결정적 본문으로 종료한다.

마감은 SMTP 시도 개시의 목표다. DNS·SMTP 장애가 있으면 수신함 도착을 보장하지 않는다. 결과를 저장하고 실패로 보고한다. 전송 결과가 불확실할 때 자동 재발송하면 중복 가능성이 있으므로 pending/sent/failed 외 unknown을 구분해 재시도 정책을 정한다. SMTP만으로 exactly-once 배달을 약속하지 않는다.

### 자원

HTTP 소스별 동시성, LLM 호출, Docker 실행 수를 별도로 제한한다. 시작은 현재보다 공격적인 동시 호출을 늘리지 않는 설정이다. Retry-After는 존중하고 장애 소스는 대기시키며 독립 작업을 진행한다. arXiv 재시도 결함 수정은 별도 예정 작업이며 완료 전 대규모 실험을 진행하지 않는다.

재현 시작 전 자원 입장 제어는 기존 launch_background 소유 경로에 둬야 한다. 외부 루프에서 _process_paper를 무제한 병렬화하면 Docker도 같이 늘어나므로 금지한다. 시작과 대기를 분리하는 변경은 재현 실행 핸들·시도 ID·결과 귀속을 먼저 설계하고 진행한다.

### 재시작과 결과 귀속

작업 멱등 키는 논문 ID만이 아니라 입력 버전·행동 종류·정책 관련 버전을 포함한다. SQLite 트랜잭션으로 작업을 점유하고, 실행 식별자와 heartbeat 또는 확인 가능한 프로세스 정보를 연결한다. running 표식만 사라졌다고 성공하지 않는다. 옛 성공 결과나 다른 시도의 로그를 현재 시도의 성공으로 잘못 연결하지 않는다.

재시작 시 남은 전체 마감은 최초 실행 시각과 저장된 마감으로 복구한다. 프로세스 내 경과 시간은 monotonic clock을 사용하되 그 값을 다른 부팅에 재사용하지 않는다. 마감 후 늦게 나온 재현 결과는 저장하되 이미 만든 메일 스냅샷을 바꾸거나 다음 메일에 과거 상태 소식으로 넣지 않는다.

## 10. 단계별 구현·진입 조건

### A. 계약과 기준선 고정

산출물: 상태 스키마, 허용 행동 표, 전체 마감 설정안, 비교에 쓸 고정 후보·공개 원문 스냅샷. 현행 선택·메일 양식을 기준 출력으로 보관한다. ‘초록만 있음’, ‘수치 불일치’, ‘재현 시간 초과’를 구분하는 실패 사례를 고정한다.
완료 조건: 현재 동작과 추가 설계가 혼동되지 않고, 비교 입력을 다시 만들 수 있다.

### B. 결정적 상태·마감 제어

산출물: 기존 루프 내 작업 기록과 전체 deadline 전파, 재현 시도 결과 귀속, 결정적 다음 후보 선택. 아직 LLM으로 순서를 바꾸지 않는다.
완료 조건: 가짜 시계·실제 운영 함수 테스트에서 여러 논문의 대기가 전체 마감을 넘겨 누적되지 않고, 재시작·중복 시작·옛 결과 재사용 오류가 검출된다. 네트워크가 막혀도 시간 내 저장·전송 시도 또는 명시적 실패로 종료한다.

### C. LLM 선택기의 shadow 평가

산출물: 허용 후보에서 다음 대상을 고르는 무료 LLM 제안기. 기본 정책이 실제 실행하고 모델 제안은 실행하지 않으며 로컬에 비교 기록만 남긴다. shadow도 외부 API를 쓰므로 재생 모의 모드와 구분한다.
완료 조건: 잘못된 ID, 위조 근거, 소스 내 지시문, 모델 장애가 도구 실행으로 이어지지 않는다. 제안 형식 유효율과 추가 지연·호출량을 측정한다. 미측정 개선을 주장하지 않는다.

### D. 제한된 agent 모드

산출물: 검증된 제안을 실제 다음 PROCESS_PAPER 선택에 반영한다. 실행 결과가 바뀌면 선택이 바뀌는 경로를 시험한다. --policy fixed|rules|agent, --shadow 같은 옵션 이름은 구현 후보다. 기본은 평가 전 fixed로 둔다.
완료 조건: 도구 결과를 반영하는 행동 선택 이력을 재생할 수 있고, LLM 중단 시 같은 실행 안에서 rules로 돌아가 최종화할 수 있다. 모든 선택을 모델 응답만 따라가는 구조로 만들지 않는다.

### E. 근거별 행동과 방법론 평가

D에서 품질 대비 비용의 가치가 확인된 뒤 추가 검색·대체 본문·특정 근거 확보를 노출한다. _process_paper 단계 분리의 회귀 위험을 별도로 검토한다. 이 단계가 관찰–근거–행동 의존관계 기반 방법론의 본 실험이다.
완료 조건: 고정 입력 비교에서 사전 정의한 품질·지연 지표를 보고하고 불리한 결과도 남긴다. 논문 단위 D의 결과를 근거 단위 E의 성과로 쓰지 않는다.

### F. 운영·Raspberry Pi 검증

현재 로컬 환경에서 소규모 운영을 먼저 확인한다. 이후 Pi 모델·RAM·OS·CPU 아키텍처·Docker 가용성을 실측한다. 무료 LLM API 호출과 스케줄링은 보드에서 수행하되, 각 외부 연구 코드의 ARM·GPU 지원은 별개로 판정한다. 이전 .venv를 복사하지 않고 대상 환경에서 의존성을 재구성한다. ARM 지원 불명은 실패로 단정하지 않고 미확인으로 기록한다.
완료 조건: 재부팅 후 복구, 중복 cron, DNS 실패, 저장 공간 부족, 시간 동기화, Docker 불가를 검증한다. 24시간 전원 유지가 서비스 가용성 보장이라는 주장은 하지 않는다.

고정 개발 일수는 제시하지 않는다. 큰 불확실성은 재현 작업 수명 관리와 단계 분리다. 가장 작은 에이전트 시제품은 A~D이며, 특허 후보의 구체화는 E에서 검증한다.

## 11. 테스트 계획과 무엇을 망가뜨리면 실패하는가

| 시험 | 실제 호출할 경로 | 깨뜨리면 실패해야 하는 것 |
|---|---|---|
| 허용되지 않은 선택 | 후보 검증→기존 실행 루프 | 임의 ID·함수명을 실행하는 변경 |
| 결과에 반응하는 선택 | 같은 후보, 다른 실제 도구 결과를 주입 | 관측을 무시하고 최초 순서만 쓰는 변경 |
| 반복 제한 | 같은 입력 버전으로 실패를 반복 | 미해결 상태에서 같은 행동을 무한 재시도하는 변경 |
| 전체 마감 | 가짜 시계와 _process_paper/대기 함수 | 매 논문에서 전체 deadline을 새로 만드는 변경 |
| 완료 결과 귀속 | 다른 시도 ID·옛 로그·마커 없음 | 로그 부재나 과거 성공을 현재 성공으로 기록하는 변경 |
| 미확인 표현 | 실제 digest 두 렌더러 | exit 0을 성능 재현 완료로 표시하는 변경 |
| LLM 장애 폴백 | 파싱 오류·429·timeout 주입 | 정책 실패가 전체 메일 생성 중단으로 번지는 변경 |
| 상태 복구 | 임시 SQLite와 중단 후 재시작 | 완료 작업 중복 실행·기존 마감 초기화 |
| 메일 형식 | HTML 파싱·MIME 조립 | 동향 순서·논문 토글·과거 소식 제외 계약 파괴 |
| 전송 불확실 | 실제 _deliver에 SMTP 결과 모의 주입 | 실패/unknown을 sent로 승격하는 변경 |
| 전송 데이터 경계 | 제안기 실제 직렬화 payload | 비허용 필드·원시 로그·시크릿 표본 포함 |

테스트는 프로덕션 함수를 호출하고 정책 계산을 테스트 안에 다시 구현하지 않는다. 각 구현 단계에서 관련 테스트 후 전체 .venv/bin/python -m pytest green을 확인한다. 오프라인 오류는 원인을 구분하고 통과했다고 쓰지 않는다. eval 기준선 이동, 검증 임계값 완화, 테스트 삭제로 통과시키지 않는다.

## 12. 논문 실험 설계

비교군은 F: 현재 고정 순서, R: 근거 상태를 쓰는 결정적 정책, A: 동일 후보·동일 상태에 LLM 선택 추가다. 첫 비교에서는 행동 공간도 같게 맞춘다. A만 추가 검색을 허용하면 선택 방식의 효과와 도구 추가의 효과가 섞인다. 후속 E에서는 공유 근거 연결 제거, 관측 피드백 제거의 ablation을 별도로 수행한다.

최소 예비 실험 규모 제안: 공개 논문 20~30편의 고정 풀과 복수 관심 프로필 조건. 이는 계획값이며 확보된 표본이 아니다. 무료 예산 안에서 복수 실행을 하고 프롬프트·모델 식별자·실행 시각·응답을 기록한다. 평가자 가능 인원을 확인하고, 가능하면 두 평가자가 방법 이름을 가린 결과를 독립 평가한다. 한 명이면 그 한계를 명시한다.

주요 지표:
- 주장 지지율: 원문이 지지한 평가 대상 주장 / 평가한 주장. 인용 형식 유효율과 별도다.
- 근거 충족 범위: 사전에 정한 평가 질문 중 확인할 자료가 확보된 수 / 전체 질문. 에이전트가 스스로 쉬운 질문만 만들어 분모를 줄이지 못한다.
- 유용성: 연구자가 유용하다고 평가한 추천 / 평가한 추천. 익숙한 내용과 무관한 내용을 별도 기록한다.
- 마감 준수: 설정한 마감 내 최종화 또는 SMTP 시도를 시작한 실행 / 전체 실행. 실제 도착과 구분한다.
- 자원: 정책 포함 LLM/API 호출, 전체 경과 시간, 중복 작업, Docker 점유 시간.
- 에이전트 동작: 유효 선택, 거절·폴백, 결과 관측 후 선택 변화. 선택이 달라졌다는 사실 자체를 품질 개선으로 쓰지 않는다.

후보·원문·도구 응답을 고정한 재생 실험은 결정 경로 비교에 사용하고 실제 API 운영 지연으로 해석하지 않는다. 라이브 실험은 출처 변동과 무료 API 상태를 기록한다. 실패·timeout 실행을 분모에서 빼지 않는다. 사전 평가 기준과 허용 지연은 데이터 확인 전에 고정한다. 현재 모든 제안 방법의 개선 수치는 미실측이다.

## 13. 논문과 특허의 연결 및 선행기술

[ReAct](https://arxiv.org/abs/2210.03629)는 추론과 행동을 결합하는 LLM 접근을 다룬다. 따라서 ‘결과를 보고 다음 도구를 고른다’ 자체를 새 발명으로 주장하지 않는다. [Anthropic의 에이전트 설명](https://www.anthropic.com/engineering/building-effective-agents)은 고정 워크플로와 동적 도구 선택을 구분하는 설계 참고로 쓴다.

[마감 인지 작업·동작 계획 연구](https://arxiv.org/abs/2410.05828)는 제한된 시간에 계산 노력을 배분하는 메타추론을 다룬다. [US12461725B2](https://patents.google.com/patent/US12461725B2/en)는 기대 가치 기반 스케줄링 관련 선행 특허다. 따라서 시간·예상 가치·작업 선택의 넓은 조합도 우리만의 것으로 단정할 수 없다.

우리 후보는 관찰별 미충족 근거 집합, 공유 근거의 중복 없는 기여, 실제 실행 결과로 갱신되는 허용 행동, 마감에 따른 출력 범위 제한의 결합이다. 이것을 구현 가능한 자료 구조와 전이 규칙으로 좁히고 가장 가까운 청구항과 구성요소별 대응표를 만든다. 단순 도메인 치환인지, 기술적 처리 차이가 있는지 검토한다. 한국 대응 출원·전체 청구항·법적 상태·실시자유 조사는 아직 하지 않았다.

논문은 F/R/A의 비교와 시스템 한계를 보고한다. 내부 발명신고서는 기술 문제, 실제 구현, 추가 설계, 발명자 기여, 공개 이력, 선행기술과의 차이를 구분해 작성한다. 일반적인 계획–실행 루프나 ‘에이전트’ 명칭 자체를 기여로 내세우지 않는다. 외부 제출·공개·출원은 이번 계획 작성에 포함하지 않는다.

## 14. 승인 후 가장 먼저 할 작업

A의 상태·행동 계약과 B의 전체 마감 처리를 먼저 구현한다. 이어 C의 shadow 제안기를 붙여 정책 호출 비용과 제안 유효성을 확인한다. D까지 통과해야 실제 에이전트 동작을 평가할 수 있다. 근거별 세부 행동 E는 그 결과를 보고 진행한다.

구현 전 확정할 항목은 메일 전체 마감, 민감 모듈 변경 범위, 무료 API 실험 예산과 실제 발송 대상이다. 현재 메일 레이아웃, 무료 원칙, 검증 판정 소유, 과거 상태 소식 제외는 확정된 요구로 유지한다. 이번 계획서 작성만으로 운영 DB 마이그레이션이나 실험 메일을 실행하지 않는다.
