# 기존 일일 메일 + "이번 주 참고할 만한 연구 자료" 절 — 계획 v5 (2026-10-25, 최종 방향)

상태: **계획만 — 운영 설정·코드는 바꾸지 않는다.** v5 가 아래 v4·v3·부록 v2 보다 우선한다.

## v5-0. 왜 또 바꾸나 (경과를 그대로 남긴다)
논의가 세 번 지나치게 흔들렸다: 과업·병목·실습(업무 지시형, 1회차) → 정보 세 줄(도구 소개형, Claude 안·미채택) → 주간 심화 해설(장문 분석형, 2회차 19:29).
사용자(외부 의견 승인): 2회차 장문 분석은 **채택하지 않는다** — 이미 있는 일일 "오늘의 연구 흐름"·핵심 논문 분석을 다시 하는 별도 보고서가 됐고, 비전은 공통 인용이 없다는 이유로 빠졌다
(쓸 만한 공개 자료가 있어도 빠지는 구조는 목적과 맞지 않다). 장문 분석은 내부 자료로만 남긴다(`docs/PILOT_round2_weekly_insight.md`).

## v5-1. 목표
**기존 메일 100% 유지 + 좋은 연구 자료를 찾는 별도 검색·검증 경로 + 짧고 유익한 주간 참고 자료 절.**
받는 사람이 "이런 중요한 논문이나 구현 자료도 있었구나, 우리 연구에 참고할 만하겠다" 고 느끼게 하는 것.

## v5-2. 원칙
1. 일일 메일의 연구 흐름 분석·핵심 논문·근거 검증·구성·순서는 바꾸지 않는다. 주간 참고 자료 절만 추가한다(자리: 핵심 논문 카드 뒤).
2. 주간 경로는 **독립적으로** 자료를 찾는다 — 브리핑에 실린 논문으로 범위를 묶지 않는다. 기초 논문·공개 구현·모델 체크포인트·데이터셋·벤치마크·공식 튜토리얼.
3. 공동 인용은 **발견 경로 중 하나**일 뿐 선정 조건이 아니다. 분야에서의 중요성·실제 참고 가치·현재 연구와의 관련성을 종합한다.
4. 과업 목록(v3-2)은 내부 관련성 판단에만. 메일에 과업 ID·병목·다음 행동·활용 결과 요청 없음.
5. 자료마다 간결하게: 무엇인지 · 어떤 연구 문제·배경에서 중요한지 · 참고할 코드·모델·데이터·문서. 필요하면 기존 방식과의 차이 한두 문장. 매번 장문의 기술 발전사를 쓰지 않는다.
6. 프로필당 주 1회 1~3건, 적합한 게 없으면 비운다. 이미 보낸 자료는 의미 있는 업데이트 없이 반복하지 않는다.
7. 사실·공식성·라이선스·접근 제한·자료 간 관계는 부록 v2 의 독립 검증 구조를 유지한다. 검증 절차를 메일에 늘어놓지 않고 필요한 사실과 중요한 제약만 표시한다.
8. 연구동향 분석과 주간 참고 자료 탐색은 서로 보완하는 기능이다 — 주간 절을 위해 2~3주 논문 전체를 다시 분석하지 않는다.
9. 반응은 기존 반응·프로필 적응과 분리(부록 6절의 `asset:` 분리 과제 그대로). 평가는 "새롭고 유용한 자료를 실제로 발견했나, 정보 품질은 충분한가".

## v5-7. 운영 방식 확정 — 화·목 참고 자료 절 (2026-10-26 사용자 승인, 10/29 시범)
**역할**: 매일 = 연구 분야의 변화(기존 일일 동향 그대로) / 화·목 = 지금 공부하거나 활용할 자료 / 세미나 = 그중 새 핵심 아이디어를 연구자가 골라 논의.
- 일일 메일의 검색·순위·프로필 적응(키워드·가중치·주간 관리)은 바꾸지 않는다. **과업 정보는 검색 키워드에 넣지 않는다.**
- **화·목 일일 메일 안에 "참고 자료" 절**(확정 형식, 핵심 논문 카드 뒤)을 붙인다 — 별도 메일을 늘리지 않는다. 프로필당 0~2건. 가치 있는 후보가 있으면 주 1회 추가 가능.
  0건 허용 — 횟수를 채우려고 억지로 추천하지 않는다. 처음 대상은 team_robot·team_agent(비전은 실제 과업 목록을 정리한 뒤 확대 — 영구 제외 아님).
- **선정 우선순위**: 과업 목록(로봇 RB-01~06, 에이전트 AG-01~05)에 닿는 자료가 먼저, 최근 4주 동향 상위 주제의 기초 자료는 보완. 새 논문이 아니어도 된다(기초 자료·공개 구현·튜토리얼).
- **정보만 준다**(사용자 10/24·10/26): 무엇인지 · 무엇을 이해하는 데 도움이 되는지 · 공식 출처에 적힌 사실(공개 코드·가중치·예제·데이터·라이선스·**문서에 명시된 요구 환경**) · 링크.
  팀 장비에서 돌아가는지, 도입이 쉬운지, 제조 과제에 쓸 수 있는지는 **판단해서 적지 않는다** — 연구자가 판단한다. 실험 순서·논의 질문도 넣지 않는다.
  "공개 구현이 있다"와 "우리 환경에서 쓸 수 있다"를 같은 뜻으로 쓰지 않는다.
- **탐색과 추천을 분리**: 과업 후보는 필요할 때 더 자주 모아 후보 저장소에 쌓고, 추천하지 않은 자료도 지우지 않는다(과업이 바뀌면 다시 평가).
- **이력 분리**: 소개함(발송 기록) / 활용함(**팀이 실제로 썼다고 확인했을 때만** — 클릭·긍정 반응으로 자동 판정 안 함) / 세미나 선정. 소개한 자료는 의미 있는 업데이트 없이 반복하지 않는다.
- 사실 확인은 v5-6 기준(공식 원문·라이선스·접근 조건, Codex 사실 대조) 그대로.
- **10/29(목) 시범**: 로봇 RB-05(손 리타게팅), 에이전트 AG-01(결정표)·AG-04(구조화 출력·검증) 후보를 검토해 기준을 넘는 것만 싣는다. 확인할 것 — RB-05 는 공식 자료가 입력·출력 관절 매핑 방법을 설명하는가,
  AG-01 은 AI 출력으로 판단 규칙을 구성하는 데 참고할 자료인가, AG-04 는 출력 스키마·검증·오류 처리의 실제 구현 근거가 있는가, 공통으로 사실 출처·중복·라이선스·설명의 구체성.
- **판단 기준(목표 수치 없이)**: ① 기존 일일 동향이 손상되지 않았는가 ② 현재 과업에 도움이 되는 검증 가능한 자료를 새로 발견했는가 ③ 연구자가 가치 있는 자료를 골라 분석·세미나로 이어 갈 수 있는가.
  처음 2~3주에는 과업 부합 비율·공개 구현 근거 확인 비율·중복 비율·연구자 평가(반응 수단 전까지는 회신으로)·세미나로 이어진 건수를 기록만 한다.
- 운영 코드(후보 저장소·이력 장부·`asset:` 반응 분리)는 아직 구현하지 않는다 — 시범은 수동(Claude) 실행.

**측정**
- 추출(입력별): 추출 건수, 근거 문장이 입력에 실제로 있는 건수, 참조 목록 일치 건수, 관계 오류, **입력에 애초에 없는 자료**(놓침이 아니라 정보 부족으로 따로 셈 — 이름이 그 입력에 나오는지는
  Python 문자열 대조로 판정), 참조에 없지만 원문으로 맞다고 확인된 새 발견.
- 초록 경로(비전 중심)는 원문 기반 수치와 직접 비교하지 않고 따로 보고한다 — 초록에 실제로 나온 자료에 대한 정확도만.
- 선별(C, 자유 추출 결과 전체에 적용): 단계별 남은 수(전체 → 유형 → 관계 확인 → 관련성 → 최종 고유 후보). 빈도 순위와 유형·관련성 순위의 최종 1~3건 비교, 제외된 후보 표본 점검.
  성과는 "바탕 모델을 몇 개 뺐나"가 아니라 "선별 뒤 소개할 만한 고유 후보가 몇 개 남았나". **0건 허용** — 채우려고 불확실한 후보를 올리지 않는다.
- 신원·공식성: 가벼운 식별(카드 참고문헌의 논문 ID)을 유형 분류 전에, 네트워크 확인은 관련성 상위 후보만(프로필당 HTTP 40회·10분 상한). 상태는
  `저자 공개처 연결 확인 / 저자 연관만 확인 / 제3자 구현 / 미확인 / 불일치` — 논문이 링크했다는 것과 그 링크가 **자기 자료 공개 문맥**(참고문헌·비교 대상이 아니라)에 있는지를 가르고,
  공식성·라이선스·접근·실행 가능성은 따로 적는다. URL·근거 문구·조회 시점을 남긴다.
- 신규성 셋: ① 참고자료 절 미소개 ② 일일 카드 미언급 ③ 팀이 몰랐던 자료(D 에서만). 실패 분류: 입력 없음 / 후보 없음 / 추출 실패 / 신원 미확인 / 연구 부적합.
- 비용: 호출 수·시간·실패·재시도, 사람 시간.
- D 팀 검토: 최종 후보 8~12건, 자료명·한두 문장 소개·링크만, 순위·방식·출처 경로를 가린 검토표. 선택지 `읽을 만함 / 이미 알고 있음 / 소개 가치 낮음`. 결과가 없으면 팀 적합성은 미검증.

**Codex 계획 검토 반영(2026-10-25, 지적 12건 전부 채택 — 근거 확인 뒤)**

  (예: 자료명 π0.5 ↔ 원문 `\pi_{0.5}`). 자료가 입력에 있는지와 그 관계의 근거가 입력에 있는지를 따로 판정한다. 비율에는 분모를 함께 적고 분모 0 은 "계산 불가".

  입력 효과는 같은 sonnet 추출기 결과끼리만 비교한다.

## v3-0. 최상위 원칙 (사용자 지시 2026-10-24)

1. **과업·병목 기준 선정** — 모든 후보는 현재 과업(아래 v3-2) 하나 이상에 연결되고, 그 과업의 **어떤 병목을 줄이는지**와 **써 본 뒤 확인할 결과**를 함께 낸다.
   과업에 연결되지 않는 유명 논문·새 프레임워크는 그 자체로 추천 이유가 아니다. 과업 ID 와 자료 근거를 잇지 못하면 보류, 어떤 문제를 푸는지 설명 못 하면 추천하지 않는다.
2. **신뢰성은 독립 검증** — 사실(자료·코드·가중치·라이선스·접근 조건)은 Python·원천 자료로, 관계(공식 구현·체크포인트·데이터)는 독립 규칙으로 확인한다(부록 4절).
   모델이 "관련성이 높다" 고 주장하는 것만으로 확정하지 않는다.
3. **활용성은 다음 행동으로 제시** — "도움이 될 것" 이 아니라 "이 과업에서 무엇을 해 보면 되는가(다음 행동)·무엇이 필요한가·무엇을 확인하면 되는가".
4. **실제 활용은 후속 기록** — 메일 버튼 "검토해 보겠다" 는 의향이다. 실제 활용은 별도로 `써봄 / 안 씀 / 못 씀(이유)` 로 기록한다. 응답이 없으면 "미확인"(안 씀으로 단정하지 않음).
   목적별 "써봄" 인정: 실습 = 실행 시도 기록·결과물 / 배경 = 연구 노트·설계 검토·세미나 준비 반영 / 아이디어 = 실험 후보·연구 질문·구현 계획에 구체 반영.
5. **과업 설정은 프로필과 독립 버전 관리** — 프로필 키워드·가중치·주간 적응과 분리된 버전형 설정. 월 1회 **그 프로필을 받는 사람**이 갱신하고 이력을 남긴다.
6. 기존 일일 브리핑·키워드·가중치·주간 프로필 적응은 바꾸지 않는다(부록 R1). `research_value`(카드 세 항목)는 과업 설정만으로 켜지지 않게 독립 스위치(부록 7절).

  일일 메일과 서로 막는다. 형식 수정본도 날짜별 최신 회차와 `profiles.last_digest` 하나를 조합한다. 별도 메일은 `mail_kind`·종류별 조회·회차별 본문 저장이 먼저 필요하다.
- (v2) 자리·날짜: 주간 결과가 준비된 뒤 **첫 일일 메일**(보통 화요일, 5.1) — "오늘의 연구 흐름" 다음, "오늘의 핵심 논문" 앞. **논문 0편 메일에도 싣는다**
  (`digest` 의 empty 분기 밖에 둔다 — digest.py:2497·3434).

### 2.3 운영 발송에 먼저 필요한 것 (v2 — Codex 지적, 코드 확인)
- **자산 전달 명세**: `asset_deliveries(issue_id, recipient_hash, unit_id, position, status, smtp_at)` — 논문 명세(`mail_issue_items`)·`profile_shown` 에 넣지 않는다.
  지금 `_deliver` 는 `papers` 만 토큰·장부에 남긴다(scan_deliver.py:104·140).
- **전달 상태 분리**: `선정됨 → 발송 대기 → 수신자별 SMTP 수락 → 전달 확정`. 부분 성공은 수신자별로 기록, SMTP 성공 뒤 장부 저장 실패는 "미발송" 으로 단정하지 않음
  (지금 장부는 총원·성공 수만 남긴다 — scan_deliver.py:128·138). 반복 방지는 "전달 확정" 만 소비한다.
- **토큰 종류 분리**: 논문 / 연구축(`axis:`) / 자산(`asset:`). `mail_reformat.load_snapshot`·`load_preview` 는 지금 `axis:` 외 토큰을 논문으로 세서
  자산 토큰이 생기면 명세 불일치로 멈춘다(mail_reformat.py:45·50·120). 자산만 있는 회차·버튼 없는 회차도 지원.
- **저장 평문 문법·역파서·공유 렌더러·형식 버전**: 자산 절을 `saved_digest` 가 같은 HTML 로 복원. 재렌더 때 지금 API 값으로 과거 사실을 다시 계산하지 않는다.
- **링크**: SMTP 직전 감사(`link_policy.audit_mail`)는 그대로 거친다. 허용 목록 밖 문서는 **자료명 + 차단 사유**로(쟁점 C).

## 4. 사실 확인 (v2 — 단독 승격 규칙 삭제)

### 4.1 관계를 종류별로 남긴다
`implements`(구현이라고 주장) · `cites`(인용만) · `checkpoint_for`(배포물) · `dataset_for` · `documents` · `depends_on` · `fine_tuned_from`/`quantized_from`.

- 저장소의 공식성: (v1 의 "README 에 arXiv 번호" 는 제3자 재구현·비교 대상·awesome 목록에도 있어 버렸다)
  `공식 확인` = 논문 본문이 **자기 구현 문맥**("our code", "code is available at")으로 그 저장소를 가리키고 **그리고** 저장소 README 가 그 논문을 자기 논문으로
  가리킴(양방향). 한쪽만이면 `주장만`. 저자 성 일치는 `저자 연관 후보`. code_ladder official(`in_text`)은 본문 링크 존재일 뿐이고, HF 카드의 GitHub 링크가 `in_text` 로
  승격되는 경로도 있다(code_finder.py:329·452) — 후보 발견에만 쓴다.
- 체크포인트: `checkpoint_for` 는 **공식 확인된 저장소·논문이 그 모델 ID 를 자기 배포물로 명시**할 때만. `arxiv:` 태그·조직명 문자열 일치만으로는 `cites`.
  기반 모델·파인튜닝·어댑터·양자화본은 별도 관계.

  공유 호스트(huggingface.co)의 같은 도메인만으로는 조직 동일성을 못 말한다.

### 4.3 문서에 적힌 조건(필요 조건)
정규식은 **추출 보조**다. 뽑을 때 목적(추론/학습/파인튜닝)·대상 버전·필수/권장·부정("필요하지 않음")·원문 위치를 함께 저장하고, 애매하면 원문 문장만 인용한다.

## 5. 선정 흐름

### 5.1 언제 돌고 언제 실리나 (v2 — R7)
- 실행: 주간 관리일 **아침 발송이 끝난 뒤** 같은 체인 끝에서 `research_assets.py --weekly`(flock 안). 아침 메일 시각에 영향 없음.
- 표시: "이번 주 결과 있음 + 아직 전달 확정 안 됨" 이면 **다음 일일 메일**(보통 화요일)에 한 번 싣는다. 실패한 날은 다음 근무일 체인 끝에서 한 번 다시
  (주간 관리 따라잡기와 같은 규칙, 같은 날 두 번 재시도 안 함 — agent_maintenance.py:1046·1064 와 같은 판정).
  수집 실패와 SMTP 실패는 재시도 정책을 따로 둔다. 지금 주간 절 데이터는 `is_weekly_review_day()` 안에서만 조립되므로(run_profile_scan.py:362)
  자산 절은 그 조건과 **독립된 표시 조건**으로 읽는다.
- 예산: **전체 절대 마감 20분**을 하위 호출에 남은 시간으로 넘긴다(v1 의 호출별 timeout 합은 1,080초 + 후보당 API 순차로 상한이 안 됐다).
  모델 입력량·API 응답 바이트 상한 함께.

### 5.2 단계
1. 후보 모으기(Python): S1·S2·S5 논문 + S3·S4 자산. 정규화 키 = arXiv / DOI / `github:o/r` / `hf-model:id` / `hf-dataset:id` / URL. 출처·검색어·순서 기록.
2. 관계 만들기(4.1): 유형 있는 관계 그래프. (v2) **연결요소를 묶음으로 쓰지 않는다** — LeRobot 같은 공용 도구가 여러 연구를 한 덩어리로 합친다.
3. 추천 단위 만들기: **특정 작업·방법·버전 + 그에 필요한 자료 집합**(예: "LeRobot 으로 SO-101 집어 옮기기" = 저장소·실습 문서·데이터셋·모델). 단위 정의는
   모델이 제안하고 Python 이 관계 그래프 안에서만 허용(없는 관계를 만들 수 없음).
4. 거르기: 전달 확정된 단위 제외(의미 있는 변화 예외), 사용자가 관심 밖 한 단위 제외. (v2) "비슷한 단위 제외" 는 유사성 기준이 생길 때까지 보류.
5. 사실 채우기(4.2·4.3).
6. 고르기·쓰기(Codex, 도구 없음): 입력 = 활용 관점·현재 단계(있으면)·단위별 사실·초록/README 발췌(근거 ID). 출력 = 프로필당 최대 3 단위, 단위마다 **목적** +
   칸별 글 + 칸별 근거 ID. 점수 필드는 없다. `research_value` 검사(ID 소속·숫자·단정·일반론) 재사용.
7. 검증(Claude, 도구 없음, `external_verify` 와 같은 격리): (v2) 칸마다 세 가지 — ① 인용 원문이 주장을 지지하나 ② 사실과 제안이 구분되나 ③ 현재 단계·활용 관점에
   맞나. 판정 빠짐·중복 ID·모르는 ID·다른 단위 근거는 **불통과**. 사실 칸 승격 금지.
8. 목적별 필수 칸(5.3) 미달이면 단위를 뺀다. 결과·입력 버전·탈락 사유·표시 순서를 저장.

### 5.4 모델 호출과 한도 (v2)

자산 경로 추가: 선정 1 + 검증 1(S6 끔), S6 켜면 +1. 한도 오류가 나면 같은 체인의 뒤쪽 선택 호출(자산 경로)은 그 주 건너뛴다(`narrative_engine._codex_blocked` 와
