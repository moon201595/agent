## 1. 계획서의 원래 요구사항

계획 v2의 정확한 위치는 `docs/AGENT_PLAN_2026-09-14.md:169-190`, §6이다. 요구사항 전문을 그대로 인용한다.

> 뜻: "과제 목표를 주면 baseline 추천"이 아니라 **사용자 관심 분야별로 "지금 무엇이 SOTA 인가"를 알려주는 것** — 예: 비전 검사(이상 탐지)에서
> 어떤 모델이, 로봇 조작(VLA)에서 어떤 용도로 어떤 모델이, VLM·온디바이스 추론에서 무엇이.
>
> **정직한 표현이 핵심**: 메일에는 "현재 SOTA" 단독 표현을 쓰지 않고 **"(벤치마크·분할·지표·프로토콜) 기준 최고 후보 + 근거 등급 + 확인 날짜"**로 쓴다.
>
> - **트랙**: 프로필의 core 키워드 묶음에서 분야·용도·데이터 형태·배포 제약으로 만든다(키워드 하나 = 트랙 하나가 아니다). Python 이 묶음 후보 →
>   Claude 가 빠진 트랙·벤치마크 후보 제안 → GPT 가 중복·표기 변형 비판 → **사용자가 한 번 확인한 트랙만 활성**. 벤치마크를 모르면 `benchmark_unknown`.
> - **비교키**: 트랙 · 용도 · 데이터셋(+버전) · 분할 · 지표(+방향) · 평가 프로토콜(학습 방식·추가 데이터·앙상블) · 모델 범위 · 기준 날짜.
>   비교키가 다르면 최신 논문이라도 승자를 바꾸지 않고 `비교 불가`.
> - **근거 등급**: A 공식 리더보드·챌린지(버전·분할·갱신일 확인) · B 벤치마크 공식 보고·독립 평가 서버 · C 논문 결과표의 같은 조건 행(저자 보고값) ·
>   D "state of the art" 문장만(판정에 안 씀) · E 블로그·검색 스니펫(후보 발견용만). 리더보드 갱신일이 90일 넘으면 `stale`.
> - **자료 결합**: 우리 DB 의 검증 통과 요약 결과 절(원문 비교표 수치)을 먼저 후보로 쓰고(`trend_report.result_excerpts` 조건 재사용), Claude 웹 조사로
>   리더보드·최신 논문을 보강한다. 둘이 다르면 덮어쓰지 않고 둘 다 저장. 원문 URL·위치·접근일·내용 해시 없는 수치는 저장하지 않는다.
> - **변화 감지**: 스냅숏은 append-only. 변화 유형 new_winner · metric_improved · protocol_changed · evidence_upgraded/downgraded · no_change · incomparable.
> - **빈도**: HOT 트랙 매주 · WATCH 월 1 · COOL 분기 1 · 사용자가 "지금 확인" 요청 시 즉시 1회(주간 예산 앞당김). 매일 전체 검색은 하지 않는다.
> - **메일**: 주 1회, 트랙당 한 줄·최대 3줄 — 예: "비전 검사 / 산업 이상 탐지 — MVTec AD · 이미지 AUROC · test 기준 최고 후보 Model X(저자 결과표 기준,
>   리더보드 교차확인 미완료) [출처]" · "로봇 조작 / VLA — 같은 조건 비교 근거 없음: 이번 주 판정 불가(마지막 확인 날짜)".
> - **저장**: `sota_tracks` · `sota_sources`(URL·종류·접근일·해시·등급·위치) · `sota_results`(모델·데이터셋·분할·지표·값·프로토콜·보고 주체) ·
>   `sota_snapshots`(비교키 해시·상태·변화 유형) + `sota_snapshot_winners`(공동 최고).
> - **분담**: Claude 조사·후보 정리 · GPT 같은 조건인지·자기주장인지·오래됐는지 감사(승자 확정 안 함) · Python 비교키 정규화·지표 방향 비교·스냅숏·메일 3줄.

**확정:** 목표는 관심 분야·용도별로 같은 평가 조건의 **최고 후보와 확인 상태를 주간 최대 3줄** 알리는 것이다. 전체 순위표나 수신 논문의 “N위” 표시는 §6에 요구되지 않았다. 공동 최고·비교 불가·시점별 변화까지 저장하려 했으며, 논문 자체 SOTA 문장은 D등급으로 승자 판정에 쓰지 않는다(계획:174-190). 따라서 자료원이 생겨도 현재의 자체 주장 추출기를 순위 API로 갈아 끼우는 것만으로는 요구를 충족하지 못한다.

보류 근거는 `docs/PROGRESS.md` §8-133(`:5768-5776`)이다. Papers with Code 리다이렉트/API 부재와 HF API 내용은 **2026-09-16 기록**이지 이번 조사에서 재확인한 사실이 아니다. 당시 6/120편 등의 수치도 역사적 기록이며 재측정하지 않았다.

## 2. 지금 있는 것

### 2.1 추출기와 벤치마크 이름

`sota_claims.py:23-40,79-86`은 영어 정규식으로 성능 주장(achieve/attain/reach/obtain/set/establish/deliver/yield/report + SOTA, SOTA + 성능 명사, outperform/surpass/exceed/beat + SOTA, new state of the art, first to achieve, outperform/surpass + all/every/existing/prior/previous)을 찾는다. `we/our/ours/the proposed/this paper` 등의 자기 주장 단서가 필수다. 부정 표현과 과거 연구 표현을 제외하고, 배경 표현은 outperform류 동사가 없을 때 제외한다. 의미 검증이나 순위 비교는 하지 않는다. 특히 `first to achieve`도 포함되므로 모든 결과를 실제 SOTA로 받아들일 수 없다.

`extract`는 공용 문장 분할 후 600자 초과 문장을 제외하고, 동일한 비어 있지 않은 벤치마크 튜플의 문장을 중복 제거한다. 최대 3개 주장, 문장당 240자 뒤 말줄임표를 반환한다. 형식은 `[{index: 원문 문장번호, sentence: 문장, benchmarks: [문자열]}]`이며 순위·점수·지표 방향·분할·프로토콜 필드는 없다(`sota_claims.py:17-18,89-104`).

벤치마크는 대소문자를 구분하는 `on (both/all)? (the)? <대문자 시작 이름>`과 `across/on … benchmarks/datasets: A, B, C` 목록에서 뽑는다. 전치사 이후와 dataset/benchmark 등의 끝말을 제거하고, 복수 단어면 각 단어 첫 글자가 대문자 또는 숫자인지, 단일 단어면 두 번째 글자 이후 대문자/숫자가 있는지 검사한다. 최대 3개이며 정확 문자열로만 중복 제거한다. 쉼표 등은 정규식 캡처 자체를 끊거나 후속 분리로 처리한다. 이것은 벤치마크 사전 검증이 아니다(`sota_claims.py:42-76`).

**로컬 재현 R1:** `python3 -B`에서 실제 `sota_claims.extract(f'We achieve state-of-the-art results on {x}.')`를 호출했다. 추가 파일·DB 쓰기 없이 다음 결과를 얻었다.

| x | 반환 benchmarks |
|---|---|
| MVTec AD | `['MVTec AD']` |
| MVTec-AD | `['MVTec-AD']` |
| MVTecAD | `['MVTecAD']` |
| mvtec ad | `[]` |

따라서 세 표기는 현재 하나로 묶이지 않는다. 소문자 표기는 주장 문장만 남고 벤치마크는 비게 된다. R1은 합성 문장으로 파서 동작만 확인한 것이며 실제 논문 커버리지·정밀도는 **미실측**이다.

`claims_for`는 papers의 text_path 원문을 먼저 읽고, 읽기에 실패하거나 경로가 없으면 초록으로 대체한다. 원문이 읽히지만 추출 결과가 빈 경우에는 초록을 다시 검사하지 않는다. 초록 결과의 index는 None이다. DB 연결은 일반 `sqlite3.connect(db)`이고 조회만 하며 별도 주장 테이블에 저장하지 않는다(`sota_claims.py:107-127`). 이번 조사에서 이 함수로 운영 DB를 열지는 않았다.

## 3. 자료원이 만족해야 하는 조건

아래에서 **확인**은 현재 코드/조회 결과이고, **도출·제안**은 그 사실과 §6을 만족시키기 위한 설계 판단이다. 새 어댑터·테이블·스케줄은 아직 구현된 기능이 아니다.

### 3.1 프로필 → 트랙 → 자료원 task 연결

**확인:** 현재 키워드 매처는 제목+초록에 제한된 구분자와 단어 경계 정규식을 적용한다(`profile_scoring.py:48-94`). `concept_key`는 소문자화와 구분자 정리, robotic→robot, large language model→llm, llm-based→llm 세 치환을 한다. 호출 목적은 `concept_breadth`의 개념 수 집계이지 외부 task taxonomy 조회가 아니다(`profile_scoring.py:332-349`).

**로컬 재현 R3:** `python3 -B`로 `profile_scoring.py`를 AST 파싱하여 `_CONCEPT_FOLDS` 대입과 실제 `concept_key` 함수 노드만 compile/exec한 뒤 호출했다. 전체 모듈을 불러오는 부작용 없이 원본 함수 본문을 실행했다. 결과:

```text
'MVTec AD' -> 'mvtec ad'
'MVTec-AD' -> 'mvtec ad'
'MVTecAD' -> 'mvtecad'
'defect detection' -> 'defect detection'
'anomaly detection' -> 'anomaly detection'
'LLM agent' -> 'llm agent'
'large language model agent' -> 'llm agent'
'vision-language-action' -> 'vision language action'
'VLA' -> 'vla'
```

**도출:** `concept_key`는 후보 별칭의 일부 표기 정리에 재사용 가능하지만 `defect detection`과 `anomaly detection`의 관계, VLA의 풀어쓴 명칭, 특정 벤치마크와 분야의 관계는 결정하지 못한다. 이들을 무조건 동의어로 합치는 것도 정당화되지 않는다. 자료원에는 안정적인 task/benchmark ID와 설명·버전·평가 조건이 있거나, 우리 쪽에서 검토한 별칭 및 대응표를 만들 수 있을 만큼의 근거가 있어야 한다. `프로필 core 묶음 → 사용자 확인 트랙 → 자료원 task ID → 비교 조건`을 명시적으로 연결하는 작업이 필요하다(계획:176-179, R3).

`term_hygiene.norm_tokens`의 소문자·하이픈/슬래시 분해·단수화와 `token_sequence_contains`는 텍스트 후보 정리에 재사용 가능하다. 하지만 `ngrams`는 길이 2 초과 토큰으로 기본 2·3-gram만 만들고 담화/일반어를 버린다. 따라서 `AD`처럼 짧은 벤치마크 구성요소, 단일 이름을 보존할 표준 ID 정규화기로 쓰면 안 된다. task 의미 사전이나 별칭 사전도 아니다(`term_hygiene.py:106-160,176-213`).

**연결 불가 시:** 개별 리더보드를 일반 링크로 보여 주는 것은 가능하지만 “이 사용자의 관심 분야 최고 후보”라는 원래 기능은 성립하지 않는다. 연결 안 된 트랙은 `benchmark_unknown` 또는 판정 불가로 남기는 것이 계획의 계약이다(계획:176-187). 자료원 확보와 관심 분야 매핑은 별개 완료 조건이다.

| 항목 | 코드에서 확인한 수치/동작 | SOTA에 대한 의미 |
|---|---|---|

`STALE_RUNNING = timedelta(hours=3)`는 지난 running 행을 재예약할지 판단하는 기준이며 실행을 3시간에 끊는 타이머가 아니다(`agent_maintenance.py:676,688-690`). 계획 문서의 “주간 각 600초”와 실제 코드의 호출당 600초를 구분해야 한다(계획:41).

**확인:** 현재 주간 Claude 실행은 `--tools '' --strict-mcp-config`, Codex는 도구 비활성화·`web_search="disabled"`로 동작한다(`agent_maintenance.py:638-665`). 따라서 계획의 “Claude 웹 조사”가 현재 `run_week` 안에 이미 구현돼 있다고 볼 수 없다. 같은 러너에 프롬프트만 추가해도 외부 자료원 조사 기능이 생기지 않는다.

**도출·제안:** 기술적으로 일일 Python 경로에서 API를 부르는 것은 가능하지만 기존 2400초를 신규 호출의 안전장치로 믿을 수 없다. 원래 §6은 매일 전체 검색을 명시적으로 금지하고 HOT 주간/WATCH 월간/COOL 분기를 정했다(계획:185). 소스별 제한된 수집 작업으로 캐시·스냅숏을 갱신하고 메일은 저장된 결과를 읽는 편이 맞다. 직접 갱신이 필요하면 소스별 요청·바이트·페이지·재시도·전체 수집 시간 상한을 별도로 정하고 실패 시 마지막 확인 날짜 또는 미확인으로 내려가야 한다. 적정 초 수·호출량은 외부 지연/할당량이 **미실측**이므로 여기서 임의 수치를 제안하지 않는다.

주간 갱신도 아침 메일 앞에서 무제한 기다려도 된다는 뜻은 아니다. 현재 셸은 주간 관리 후 스캔을 실행하고 실패는 무시한다(`run_daily_scan.sh:75-82`). 이미 운영 진단은 발송 뒤 별도 함수로 처리하는 경로가 있다(`run_profile_scan.py:501-527`). SOTA도 갱신과 메일 읽기를 분리할 수 있으나 이는 설계 제안이다.

### 3.3 비신뢰 외부 응답의 처리 경계

**확인:** `server.py:189-212`의 HTTP 재시도·페이싱 구현 주체는 `http_client.py`다. `with_retry`는 상태코드별 재시도 및 선택적인 429 대기 합 상한을 갖지만 JSON 스키마·총 응답 크기·비교 조건을 검증하지 않는다(`http_client.py:125-171`). 이 함수 하나를 통과했다고 외부 데이터가 신뢰 가능해지는 것은 아니다.

PDF 경로에는 응답 누적 바이트 검사, 전체 다운로드 timeout, 리다이렉트 단계 검사 사례가 있다. 기본값은 **30×1024×1024바이트, 120초, 리다이렉트 최대 5회**이며 PDF 전용이다(`server.py:119-121,390-467`). URL 검사는 http(s), 최종 HTTPS, IP literal/localhost/.local 및 userinfo를 검사한다. DNS가 가리키는 실제 주소를 검사하는 코드는 이 함수에 없으므로 완전한 SSRF 방어로 확대 해석하면 안 된다(`server.py:424-444`). 일반 리더보드 JSON/HTML 응답이 자동으로 이 PDF 경로를 통과하지도 않는다.

현재 본문 저장 시 `injection_scan.scan(text)` 결과를 `papers.injection_suspect`에 기록한다(`server.py:915-926,1134-1139`). 스캐너는 bidi 문자·영어 지시문 패턴을 보고 이유 목록을 반환할 뿐 차단·무해화하지 않는다(`injection_scan.py:43-93`). 비어 있는 결과도 안전 인증이 아니다. 실제 메일 HTML 경계의 escape 사례는 `digest.py:1884-1886`, LLM에 문자열 속 명령을 따르지 말라는 명시적 지시는 `prompts/agent_propose_v1.md:35`, `prompts/agent_judge_v1.md:38`이다.

**도출·제안 경로:** 승인된 자료원 URL → 시간·크기·페이지·리다이렉트 제한 수집 → JSON/HTML을 값으로 파싱 → Python이 필드 타입/유한 수치/단위/ID/비교 조건/출처 검사 → 원본 출처·접근일·해시 보관 → 비교키와 스냅숏 계산 → 텍스트 escape 후 메일 표시. LLM이 필요할 때만 제한된 근거 필드를 데이터로 전달하고, 설명 문자열은 injection_scan으로 표시할 수 있다. 외부 값으로 명령·도구 인자·파일 경로를 실행하는 연결은 만들지 않는다. 이 공통 SOTA 어댑터는 현재 없으며 `server.fetch_paper`를 반드시 경유해야 하는 것도 아니다. 재사용할 것은 검증 원칙과 개별 장치이지 PDF 전용 함수를 JSON에 그대로 호출하는 방식이 아니다(규칙 4: `CLAUDE.md:21-22`, 위 실행 코드).

### 3.4 비용과 표현

규칙 6은 무료 API/기존 구독 안에서 운영하고 에이전트가 실패해도 메일을 보내도록 한다(`CLAUDE.md:24-25`). 따라서 유료 구독 없이는 필요한 행이나 갱신일을 얻을 수 없는 소스는 현재 범위에 맞지 않는다. 무료 한도 소진 시 캐시·재시도 지연·처리량 축소·미확인 표시가 필요하며 결제를 전제한 복구는 안 된다. 기존 자체 주장도 추출/표시 실패를 무시한다(`run_profile_scan.py:377-380`, `digest.py:542-548`). 신규 수집 실패가 스캔/메일 실패로 전파되지 않도록 같은 경계를 갖춰야 한다.

규칙 7은 검증 못 한 SOTA 수치를 사실로 쓰지 못하게 한다(`CLAUDE.md:26-27`). 자료원이 전달한 rank는 그 자료원·평가 조건·확인 날짜에 한정된 순위이지 세계 전체의 절대 순위가 아니다. 최신 갱신 시점과 접근 시점을 분리하고, 저자 보고값·공식 리더보드값·독립 재현값을 혼동하지 않아야 한다. 이는 계획의 비교키·근거 A~E·90일 stale·출처 위치/해시 요구로 구체화돼 있다(계획:178-184). 숫자가 비어 있거나 조건이 없을 때 LLM으로 채우는 경로는 허용되지 않는다.

### 3.5 저장 계약

**새 표가 필요하다.** 현재 논문/저장소 키는 한 모델이 여러 데이터셋·분할·지표에서 낸 결과, 공동 최고, 서로 다른 날짜의 승자 변경을 표현하지 않는다. repro_results는 동일 논문/저장소 키에 INSERT OR REPLACE한다(`server.py:1538-1565`); code_ladder도 교체 저장한다(`code_ladder.py:72-79`). R2에서 SOTA 표가 없고 `migrate.owners`에도 소유 모듈이 없다(`migrate.py:31-42`).

도출·제안은 원래 계획의 다섯 표를 따르는 것이다: 활성 트랙/프로필 연결, 출처와 채집 버전, 비교 조건별 결과, append-only 스냅숏, 공동 최고 연결. 최소한 안정적인 source/task/benchmark/model/result 식별자, 원문 명칭, 데이터셋 버전·분할·지표/방향·프로토콜·모델 범위, 값·단위·동률 정책, 접근일·자료원 갱신일·해시·행 위치가 있어야 한다. 로컬 paper_key 연결은 별도로 두고 미연결도 상태로 보존한다(계획:176-190, `research_profile.py:675-707`).

스키마 추가는 소유 DDL과 `migrate.owners` 등록, `schema_guard.ensure` 검사, 백업 후 명시적 이관 경로가 필요하다(`schema_guard.py:70-80`, `migrate.py:31-42,139-152`). 이번 조사는 DDL·이관·백업 어느 것도 실행하지 않았다.

## 4. 쓸 수 없는 자료원의 조건

“아무 용도로도 쓸 수 없다”와 “원래 SOTA 판정에는 못 쓴다”를 구분한다. 대부분 후자이며 발견용 링크로는 남길 수 있다(계획 §6의 D/E등급, `:180-183`). 아래는 현재 저장소와 원래 계약에서 도출한 조건이지 특정 외부 서비스의 실측 평가가 아니다.

| 자료원 형태/누락 | 왜 원래 기능에 못 쓰는가 | 남는 제한적 용도·보완 조건 |
|---|---|---|
| 순위 숫자만 있고 모델/결과/논문을 식별할 수 없음 | 날짜가 바뀌었을 때 같은 후보인지 새 승자인지 연결할 수 없다. 현재도 논문 연결은 `paper_key`에 의존한다(`research_profile.py:675-706`), 계획은 모델별 결과와 공동 최고 스냅숏을 요구한다(`:184,188-189`) | 사람이 링크를 보는 용도. 안정적인 model/result ID와 근거 URL이 있으면 **arXiv ID/DOI가 없어도 분야 최고 후보 보고는 가능**하다. 다만 로컬 논문에 “N위”를 붙이는 연결은 별도 검증이 필요하다. ID 부재만으로 무조건 폐기하면 원래 요구를 과도하게 좁힌다 |
| 논문 ID 대신 제목만 제공 | 로컬 제목 대체키는 소문자·공백 정리뿐이므로 제목 수정/동명이문을 해결하지 못한다(`research_profile.py:706`). `papers`에는 DOI 전용 컬럼도 없다(R2), DOI는 search_candidates에 저장된다(`research_profile.py:166-182,967-974`) | 검토할 연결 후보로는 가능. 제목 유사도만으로 확정 순위를 붙이면 안 되며 미연결 상태를 허용해야 한다 |
| task가 자유 문자열이고 정의·고정 ID·버전·대응 근거가 없음 | concept_key/term_hygiene는 task 의미를 연결하지 않는다(R3; `profile_scoring.py:332-344`, `term_hygiene.py:119-126`). “defect detection”을 근거 없이 임의의 anomaly leaderboard로 보내면 사용자 분야를 바꿔 버린다 | 자유 문자열 **자체**는 탈락 사유가 아니다. 설명과 평가 문서가 있어 사람이 확인한 매핑을 만들 수 있으면 사용 가능. 불투명한 이름만 있으면 자동 트랙 연결 불가 |
| split/해상도/학습 데이터/추가 데이터/앙상블/모델 크기가 다른 행을 섞고 구분 메타데이터가 없음 | 동일 metric 이름이어도 비교키의 프로토콜·모델 범위가 다르므로 승자를 바꾸면 안 된다(계획:178-180). 현재 추출기 출력에는 이를 복구할 필드가 없다(`sota_claims.py:100-101`) | 각 행의 설정을 별도 근거에서 확보하기 전에는 `incomparable`. 섞여 있어도 행별 조건이 충분하면 분리해 사용 가능 |
| metric 이름/방향/단위가 없거나 rank만 있음 | AUROC와 latency처럼 비교 의미가 다를 수 있다. 원래 요구의 metric_improved를 계산할 수 없고 Python 방향 비교 계약을 충족하지 못한다(계획:178,184,190) | 같은 조건이 문서화된 공식 순위는 “자료원 보고 순위”로 제한해 인용할 수 있지만 점수 개선 추적은 불가. 단순 stars/likes는 성능 점수가 아님 |
| URL·행 위치·내용 해시로 재확인할 수 없거나 수치의 보고 주체가 불명 | 계획은 URL·위치·접근일·해시 없는 수치를 저장하지 않으며 자체 주장과 공식값을 구분한다(`:180-183,188`) | 출처 복원 전에는 발견 후보만. 단, 서버가 해시를 주지 않는 것은 문제 아님: 수집한 원문에서 우리가 계산하면 된다 |

| 유료 전용, 무료 한도가 갱신 범위를 감당 못 함 | 추가 결제 금지와 실패 시 기본 메일 보장에 맞지 않는다(`CLAUDE.md:24-25`; §3.2 예산) | 허용된 무료 범위만 추적하거나 갱신을 줄여야 한다. 실제 한도·지연은 이번 조사에서 미실측 |
| 무제한 응답/페이지·리다이렉트 또는 외부 스크립트 실행이 있어야 읽힘 | 현재 HTTP 재시도와 PDF 제한이 일반 리더보드 입력을 자동 보호하지 않는다(`http_client.py:125-171`, `server.py:390-467`) | 제한된 수집/별도 격리 경로를 구현·검증하기 전 자동 연결 불가. injection_scan 통과만으로 실행 허용 불가(`injection_scan.py:73-93`) |

**API가 없다는 이유만으로 일괄 탈락시키지는 않는다.** 원래 계획은 공식 보고·같은 조건의 논문 결과표도 B/C등급으로 인정한다(계획:180-183). 정적 표나 내려받을 수 있는 데이터도 필요한 필드·근거·수집 제한을 만족하면 어댑터 대상이 될 수 있다. 이번 조사에서는 그러한 외부 자료의 존재나 자동 수집 가능성을 확인하지 않았다.

## 5. 부분적으로 지금 할 수 있는 것

**외부 리더보드 없이 가능한 것은 자체 주장에 등장하는 벤치마크 후보의 관측 빈도 집계다. 현재 메일에 이미 있는 집계 기능은 아니며, 기존 추출기·관측 자료를 이용해 새로 구현 가능한 범위라는 뜻이다.** `sota_claims.extract`는 텍스트만 있으면 동작하고 네트워크/LLM을 부르지 않는다(`sota_claims.py:89-104`, R1). 현재 `_sota_claims`는 그날 shown 목록에 붙이는 일시 값이므로 과거 자료를 기간별로 재추출하거나 추출 결과를 별도 보관해야 한다(`run_profile_scan.py:358-384`, §2.3).

도출·제안하는 최소 집계는 다음과 같다.

1. **표본과 기간 고정:** “프로필 P가 최근 기간에 관측한 논문 중”으로 범위를 한정한다. 현재 `trend_report.observed_rows`는 search_candidates의 profile_id와 first_seen 기간으로 고르고 현재 프로필로 재채점한다(`trend_report.py:700-719`). 이는 당시 프로필로 검색한 스냅숏과는 다르다. 당시 관측 기준이 필요하면 `candidate_observations`의 profile_id/scan_id/paper_key/observed_at를 쓰고 같은 논문을 기간 안에서 중복 세지 않아야 한다(R2; `research_profile.py:284-305`).
2. **원문/초록 구분:** 본문 확보 편만 세면 표본이 줄고, 초록만 보면 초록에 안 나온 이름을 놓친다. 본문 우선·초록 대체 정책을 기록하고 자료 없음과 “읽었지만 이름 없음”을 분리한다(`sota_claims.py:107-127`). 관측 초록은 압축 보관될 수 있으므로 abstract_ref를 복구해야 한다. 이미 `observation_signals.py:48-55`가 같은 프로필·paper_key·참조 scan_id로 COALESCE하는 실행 예를 제공한다.
3. **별칭과 중복 처리:** 검토한 벤치마크 별칭만 묶고, 같은 논문에서 같은 이름은 한 번 센다. 기존 reserve_terms도 논문별 `set(ngrams(...))`를 Counter에 더한다(`observation_signals.py:67-69`). 단순 `concept_key`로는 MVTecAD가 합쳐지지 않는다(R3). 아직 별칭표가 없으면 “원문 표기별 빈도”라고 밝혀야 한다.
4. **정직한 표시:** “이 프로필의 수집 논문에서 SOTA 자체 주장에 함께 등장한 벤치마크 이름”이라고 표시한다. `extract`는 SOTA 주장 문장만, 최대 3개 주장/문장당 3개 이름을 고르므로 전체 벤치마크 언급량이나 실제 사용량과 같지 않다(`sota_claims.py:63-104`). 숫자는 Python 집계값만 쓰고 표본 수·본문/초록 범위·미관측을 함께 보여야 한다. 이전 기간 관측이 없으면 증가율을 만들지 않는 기존 사례가 있다(`trend_report.py:147-174`).

이 기능으로 얻는 것은 **관심 분야에서 추적할 벤치마크 후보를 발견하는 보조 신호**다. 자주 등장한다는 사실은 성능 1위·실제 평가 수행·리더보드 대표성을 증명하지 않는다. 예컨대 `_looks_like_name`은 대문자/숫자 형태만 검사하므로 데이터셋과 장비명을 판별하지 못한다(`sota_claims.py:53-60`). “요즘 이 벤치마크가 자주 쓰인다”보다 위의 제한된 문구가 맞다.

원래 요구의 “몇 할”인지에 대한 답: **최고 후보 판정·비교 조건 검증·승자 변화 보고라는 핵심 결과 기준으로는 0할**이다. 이것은 완성도 실측치가 아니라 §6 산출물에 대한 충족 여부 판정이다. 후보 발견 부분에는 도움이 되지만 전체 구현의 2할/3할 같은 비율을 정할 분모나 실측 근거가 없다. 따라서 전체 기여율은 **미실측·산정 불가**로 남긴다(계획:176-190; 현재 추출 출력 `sota_claims.py:100-101`).

또 다른 내부 재료는 `trend_report.result_excerpts`다. 숫자 전부 일치, measured coverage, 설정된 최소 coverage를 만족하는 요약 결과 절만 읽는다(`trend_report.py:333-374`). 그러나 반환형은 `{arxiv_id: 발췌 문자열}`이며 구조화된 모델/metric/split 결과 행이 아니다. 표 수치 후보 발견에 재사용할 수는 있어도 이 검사를 통과했다는 이유만으로 SOTA를 확정할 수 없다. 현재 DB에 특정 트랙의 같은 조건 비교표가 충분한지는 조사하지 않았으므로 **미실측**이다.

이번에는 집계 기능을 구현하거나 운영 논문 전체를 재추출하지 않았다. 따라서 프로필별 벤치마크 빈도·커버리지·처리시간 수치를 보고하지 않는다. 합성 문장 파서 결과 R1/R3와 운영 DB 스키마 읽기 R2만 실행했다.

## 자료원이 생겼을 때 착수 순서

다음은 **구현 제안**이다. 이번 조사에서 실행한 변경은 없다.

1. **응답 샘플을 §6 계약과 대조한다.** Claude가 확보한 실제 자료를 받아 task/model/result의 안정 식별, 데이터셋 버전·분할·지표/방향·프로토콜·모델 범위, 날짜·출처를 확인한다. 각 행을 “같은 조건 비교 가능/불가/후보 발견만”으로 분류한다. rank만 있는지, 점수 변화도 계산 가능한지 구분한다(계획:178-190; 본 보고서 §4).
2. **한 트랙의 대응표부터 만든다.** 프로필 core 묶음·용도와 자료원 task를 연결하고, 사용자가 확인한 트랙만 활성화한다. `concept_key`는 표기 후보 정리만 돕는다. 근거 없는 별칭 합치기 대신 미매핑을 허용한다(계획:176-179; R3). 모든 프로필에 유효하다고 일반화하기 전에 트랙별 자료 범위를 표시한다.
3. **무료 범위와 수집 예산을 정한다.** 실제 응답 지연·페이지 수·무료 한도를 근거로 별도 전체 수집 상한·캐시·백오프를 정한다. 현재 Deep 2400초/CLI 600초가 리더보드 보호장치가 아니라는 점을 전제로 한다(`run_profile_scan.py:63,217-226`; `agent_maintenance.py:607-666`). §6의 갱신 빈도를 따르고 메일은 저장된 최신 확인 결과로 만들 수 있게 한다.
4. **수집/파싱/검증 어댑터를 분리한다.** 제한된 외부 응답을 원문 근거와 함께 파싱하되, 누락 조건을 추정으로 채우지 않는다. 설명은 비신뢰 데이터, 수치 판정은 Python이다. PDF 경로와 injection_scan의 보호 범위를 일반 응답에 잘못 확대하지 않는다(`server.py:390-467`; `injection_scan.py:73-93`; `CLAUDE.md:18-26`).
5. **비교키와 append-only 저장을 만든다.** 계획의 다섯 표와 스키마 이관을 준비한다. 저자/공식/독립 평가값을 따로 저장하고 공동 최고·stale·미확인·조건 변경을 표현한다. 운영 적용은 별도 변경 범위에서 백업과 명시적 이관을 거친다(계획:178-190; `migrate.py:139-152`).
6. **실제 판정 함수를 오프라인 사례로 검증한다.** 같은 점수 동률, 방향이 반대인 지표, 다른 split/해상도/학습 데이터, 갱신일 미상, 오래된 값, ID 미연결, 별칭 충돌, 소스 실패를 입력해 승자를 잘못 바꾸지 않는지 확인한다. 파서→정규화→비교→저장→표시 운영 함수를 호출하는 검증이어야 한다. 핵심 회귀는 “조건이 다르면 incomparable”, “더 나쁜 값은 새 승자가 되지 않음”, “출처 실패가 기존 메일을 막지 않음”이다(계획:179,184,190; `CLAUDE.md:24-27`). 이번 조사에서는 테스트 추가/pytest 실행을 하지 않았다.
7. **마지막으로 주간 메일 최대 3줄을 연결한다.** 트랙당 조건·최고 후보·근거 등급·확인 날짜·출처를 표시하고, 자체 주장 줄과 섞지 않는다. 메일은 캐시만으로도 생성되게 하고 갱신 실패는 마지막 확인/판정 불가로 표현한다. 기존 텍스트/HTML 두 소비 경로를 함께 검증한다(계획:174,186-190; `digest.py:842-844,1884-1886`).

## 그래도 못 하는 것

- **세계 전체의 절대 SOTA 또는 분야 전체 N위 단정:** 연결한 자료원과 동일 비교 조건 안의 최고 후보만 판단할 수 있다. 원래 계획도 이를 제한한다(계획:174-187). 소스가 전체 후보를 망라하는지는 이번 조사에서 미실측이다.
- **누락된 평가 조건의 복원:** split/프로토콜/버전이 없으면 정규식·concept_key·LLM 합의로 동일 조건을 증명할 수 없다(`sota_claims.py:100-101`; `profile_scoring.py:339-344`; 계획:178-180).
- **과거 순위의 소급 추적:** 소스에 이력이 없고 우리도 아직 스냅숏을 저장하지 않았으면 지난 시점의 승자를 만들어낼 수 없다(R2; 계획:184,188-189). 저장을 시작한 뒤의 관측 변화만 추적할 수 있다.
- **미연결 모델을 특정 로컬 논문으로 확정:** 안정적인 식별·매핑 근거가 없으면 논문 카드의 순위나 피드백 귀속까지 연결할 수 없다(`research_profile.py:675-706`). 모델 결과 보고와 논문 연결 상태를 분리해야 한다.
- **자체 주장·숫자 일치·코드 실행 성공으로 SOTA 입증:** 현재 자체 주장 출력에는 비교 결과가 없고, 요약 발췌는 검증 조건을 만족한 텍스트일 뿐이며, repro_results는 성공/exit code/실행 단계 등만 저장한다(`sota_claims.py:100-101`; `trend_report.py:348-373`; `storage.py:113-118`). 독립 벤치마크 평가 완료와 같지 않다.
- **자료원 하나로 모든 프로필 자동 커버:** task 대응과 평가 조건이 없는 분야는 benchmark_unknown/판정 불가로 남는다(계획:176-187; R3). 실제 자료원별 분야 커버리지·무료 호출량·운영 소요시간은 Claude의 외부 조사와 후속 측정 전까지 미실측이다.

검증 범위: 네트워크 호출 없음, pytest 실행 없음, 운영 DB는 R2에서 `mode=ro`로 스키마만 조회. 운영 스캔·메일 발송·리더보드 수집·승자 계산·운영 마이그레이션은 실행하지 않았다. 보고서는 요구된 1~5절과 마지막 두 절을 순차 저장했다.
