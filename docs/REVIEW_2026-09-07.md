# paper-harness 검토와 개선안

검토일: 2026-09-07. 로컬 코드, 첨부 대화, SQLite 읽기 전용 조회, 저장 다이제스트, 실행 로그, 공식 API 문서를 대조했다. 구현 변경을 제안하는 문서이며 변경 승인을 받았거나 구현을 마쳤다는 뜻은 아니다.

## 결론

현재 시스템은 논문을 찾아 요약하고 배달하는 기반을 갖췄다. 그러나 동향의 관측 자료가 검색·선별·원문 접근·요약 처리량에 따라 달라지므로, 분야의 실제 변화와 시스템의 처리 변화를 구분하기 어렵다. 원문 확보를 모든 정보 제공의 선행 조건으로 삼지 말고, 관련 논문을 기록하는 단계와 깊게 읽는 단계를 분리해야 한다.

기존 `scan_profile` → `scan_and_digest` → `_deliver` 진입점과 SQLite를 확장하면 된다. 별도 에이전트 프레임워크나 새로운 상위 오케스트레이터가 필요한 문제는 아니다. 매일의 동향 알림을 안정화하고, 코드 실행 검토는 필요한 논문에 선택적으로 적용하는 방향을 권한다.

## 확인 범위와 실측

- 주요 실행 경로: `run_daily_scan.sh`, `run_profile_scan.py`, `find_new_papers.py`, `delta_search.py`, `s2_delta.py`, `profile_scoring.py`, `selection.py`.
- 저장·생성·표시 경로: `storage.py`, `research_profile.py`, `batch_summarize.py`, `summarize_engine.py`, `server.py`, `trend_report.py`, `digest.py`, `email_delivery.py`, `review_core.py`와 UI 관련 코드.
- 검증·실행 보조 경로: 수치/문장 검증, 철회 확인, 저장소 탐색·Docker 실행, API 계측과 관련 테스트. README와 PROGRESS의 설계 및 최근 변경 기록도 대조했다.
- `.venv/bin/python -m pytest -q`: **664 passed in 19.31s**. 이 결과는 테스트된 동작의 회귀 여부를 말하며 실제 검색 재현율·동향 정확도를 보증하지 않는다.
- 조회 시점 DB: papers 126행, summaries 120행, search_runs 46행, profiles 1행, profile_shown 31행. 지정 venue는 0행이다.
- 최신 저장 다이제스트 시각: `2026-09-07T01:53:32+00:00`. 이 시각에서 7일을 되짚어 기존 주간 SQL을 적용하면 61편이다. 그중 16편은 발표일이 이 기간보다 이전이고, 3편은 발표일이 없다. 나머지 42편은 저장된 발표일이 해당 기간 시작 이후다. 실제 출판사 발표일을 외부에서 재확인한 수치는 아니다.
- 로그에는 스케줄 실행과 발송 완료 기록이 있다. 현재 crontab 자체는 환경의 읽기 권한 제한으로 조회하지 못했다. 따라서 현재 등록 상태와 PC/WSL 중단 중의 실행은 확인하지 못했다.
- 이번 검토에서 실서비스 재스캔, LLM 요약 호출, Docker 실행, 메일 발송은 수행하지 않았다. 외부 소스는 문서를 확인했으며 모든 출판사의 실시간 수집 가능성을 시험하지 않았다.

## 우선 수정할 문제

### 1. 동향 집계가 논문의 발표보다 요약 처리 시점을 반영한다

근거: `trend_report.py:354`의 `_rows_between`은 `papers JOIN summaries`를 `s.created_at`으로 자른다. 프로필별 논문 관계 필터도 없다. `build`는 이 자료로 전주 대비 편수와 서술을 만든다.

과거 논문을 이번 주에 요약하면 이번 주 집계가 커진다. 원문을 얻지 못해 summaries에 없는 저널은 빠진다. 현재 프로필은 하나지만 다중 프로필로 확장하면 다른 프로필이나 수동 작업으로 저장한 논문도 섞일 수 있다.

개선: 발견된 후보 메타데이터를 요약 여부와 무관하게 보존한다. 발표일 기준 동향, 처음 발견한 날짜 기준 신규 알림, 요약 처리 실적을 별도 집계한다. 프로필·소스·검색 설정 버전을 함께 제한한다. 집계 창이 미완료면 증가/감소의 해석을 유보한다.

### 2. 일일 서술은 전체 후보를 보지 않으며 과거와 비교하지 않는다

근거: `run_profile_scan.py:613`은 주요 목록과 `title_only_papers`만 narrative에 넘긴다. 기본 프로필 6편과 추가 목록 최대 8편이므로 현재 구성에서 입력은 최대 14편이다. `trend_report.py:258`은 초록을 편당 900자로 잘라 최대 20편만 쓴다. 주간 자료는 생성 시각 오름차순이므로 주간 서술도 최신·대표 표본 선택 없이 앞쪽 20편이 선택된다.

프롬프트에 전주 자료나 기존 기술 흐름이 없다. 따라서 현재 출력은 관측된 몇 편의 공통점을 묶은 해석이며, 무엇이 새로 생기거나 증가했는지를 검증한 결과가 아니다.

개선: 일간에는 ‘새로 관측한 결과와 아이디어’, 주간에는 ‘동일한 관측 조건에서의 변화’를 제공한다. 전체 관측 자료에서 주제별 근거를 먼저 구성하고 LLM에는 근거 ID, 확인된 초록/본문 구절, 계산된 통계, 비교 기간을 전달한다. 표본을 줄여야 하면 주제·소스별로 대표 표본을 선정하고 실제 포함 건수를 표시한다.

### 3. S2의 `done`은 수집 완료를 보장하지 않는다

근거: `s2_delta.py:104`는 검색어당 최대 100건을 한 번 요청하고 응답의 다음 페이지·전체 건수 정보를 사용하지 않는다. `find_new_papers_since`는 일부 검색어가 실패해도 모든 검색어를 시도했다면 `done`을 반환한다.

함수 본문을 추출한 네트워크 없는 재현 결과:

```text
검색어 2개 중 1개 실패: status=done, keywords_failed=1
한 검색어에서 100개 반환: status=done, retained=100
```

두 번째 결과는 실제로 101번째 논문이 존재함을 입증하지는 않는다. 더 있는지 확인하지 않고 완료로 기록한다는 뜻이다.

또 `run_profile_scan.py:246`부터는 arXiv용 `next_since` 한 번으로 구한 창을 S2에도 사용한다. S2의 실패/partial 이력에 따른 별도 커서는 사용되지 않는다. `research_profile.next_since`의 5일 겹침은 유용하지만, 장기 장애·늦은 색인·5일을 넘긴 미처리 논문까지 보존하는 대기열은 아니다.

개선: 소스·검색어·설정 버전별 상태와 페이지 진행을 기록한다. 일부 실패, 페이지 상한 도달, 시간 초과는 partial로 남긴다. 후보 저장이 완료된 뒤 커서를 전진시킨다. 미처리 후보는 재검색에 의존하지 않고 DB 대기열에서 다음 실행으로 넘긴다. 큰 창은 날짜 구간을 나눠 복구한다. S2 bulk 검색도 검토할 수 있지만 현재 검색과 의미·정렬·누락 차이를 시험한 뒤 채택한다.

### 4. 주요 목록 자격이 원문 경로에 종속된다

근거: `run_profile_scan.py:202`의 `_eligible_for_content`는 arXiv ID 또는 OA PDF 링크가 있는 논문을 우선 자격자로 만든다. 충분한 자격자가 있으면 초록이 풍부하고 관련도가 높은 비OA 저널도 주요 목록에서 빠진다. 이는 첨부 글의 ‘관련도 순, 깊이만 구분’과 다르다.

추가 목록도 최대 8편이며 현재 렌더링에서는 빠졌다. 따라서 주요 목록에서 빠진 저널이 모두 독자에게 전달되거나 모두 서술 근거로 들어가는 것은 아니다.

개선: 중요도와 읽기 깊이를 서로 다른 속성으로 둔다. 주요 발견은 관련성과 정보 가치로 선정하고, 전문이 있는 일부에만 상세 분석을 덧붙인다. 제목만 있는 경우 성과를 추론하지 않는다. 출판사 원문 비공개와 일시적인 수집 실패도 구분한다.

### 5. 요약이 있거나 다이제스트를 만들었다는 이유로 발송 대상에서 빠진다

근거: `run_profile_scan.py:353`은 전역 summaries에 있는 arXiv 논문을 먼저 제거한다. `scan_and_digest`는 635행에서 다이제스트를 저장하고 640행에서 `mark_shown`을 호출한다. 실제 SMTP 발송은 그 뒤 `_deliver`에서 수행된다.

미리보기만 했거나 SMTP가 실패해도 주요 목록의 소비 기록은 남을 수 있다. 다른 프로필에서 먼저 요약된 논문도 아직 이 프로필에 보내지 않았는데 제외될 수 있다. 초록 정리는 별도 이력으로 저장되지 않고 최신 다이제스트만 덮어쓴다.

개선: ‘이미 요약됨’은 재생성만 막고 ‘이 프로필에 배달됨’과 구분한다. SQLite에 다이제스트 본문·HTML·대상 논문을 고정 저장하고 pending/sent/failed 발송 상태를 둔다. 실패하면 새로 생성하지 않고 같은 결과를 재발송한다. SMTP 수락과 실제 수신함 도착은 다르므로 상태 명칭도 그 범위에 맞춘다. SMTP 응답 직후 프로세스가 죽는 경계에서는 중복 가능성이 남으므로 정확히 한 번 배달을 보장한다고 표현하지 않는다.

### 6. HTML 메일에 주간 리뷰가 전달되지 않는 경로가 있다

근거: `run_profile_scan.py:630`의 주간 리뷰는 `digest_text`에만 추가된다. `_deliver`는 result로 HTML을 다시 생성하는데 result에는 주간 리뷰가 없다. `digest.generate_digest_html`에도 주간 리뷰 렌더링이 없다.

따라서 평문과 HTML을 지원하는 메일 클라이언트가 서로 다른 주간 내용을 보여줄 수 있다. 이는 코드 경로의 확인이며 실제 수신함 화면을 시험한 결과는 아니다.

개선: 일일/주간 근거를 동일한 보고서 데이터에 저장하고 두 렌더러가 같이 읽는다. HTML과 평문의 논문 ID·주간 절·출처 링크 일치 여부를 검증한다. ‘그 밖에 논문’ 목록을 복구할 필요는 없고, 서술이 실제 인용한 논문 링크만 문장 옆에 붙이면 된다.

### 7. ‘원문 커버리지’는 성공한 청크 수가 아니라 계획한 청크 수다

근거: `summarize_engine.py:694`는 두 번째 이후 청크의 실패를 잡고 부분 요약을 반환한다. 그러나 `coverage_ratio`는 성공 기록을 받지 않고 chunk_size와 max_chunks로 원문을 다시 나눠 계산한다. `server.save_summary`가 그 값을 저장한다.

외부 호출 없는 합성 재현에서 작은 청크 크기로 20청크를 만들고 두 번째 호출을 실패시켰다. 반환 요약은 첫 청크뿐인데 계산 커버리지는 1.0이었다. 운영 요약 중 몇 편에 이 문제가 발생했는지는 미측정이다.

개선: 생성 결과에 실제 성공한 청크·문장 ID, 실패 구간, 엔진, 생성 설정을 넣는다. 계획 커버리지와 실제 처리 커버리지를 분리한다. 숫자 대조 통과율도 의미적 정확도나 논문 중요도라는 이름으로 사용하지 않는다. UI 요약 경로인 `review_core._summarize_target`은 현재 사용 엔진을 `SaveSummaryInput`에 전달하지 않는 점도 함께 정리한다.

### 8. 저널·인용 데이터가 관측 자료로 보존되지 않는다

S2 응답에는 venue와 citationCount가 있다. 하지만 현재 papers 테이블에는 venue, DOI 전용 컬럼, citation_count가 없고, OA PDF 저장은 발표일·초록·저자를 비워 둔다(`server.ingest_local_pdf`). venue 채움 비율이나 시간에 따른 인용 증가를 기존 DB에서 바로 계산할 수 없다. `profile_venues`는 현재 0행이다.

`venue_hit`은 이미 찾은 후보의 가점이다. venue를 입력한다고 그 저널의 신간을 수집하는 요청이 생기지는 않는다. S2 검색은 weight 1.0 이상인 6개 비중복 키워드만 사용한다. 디지털 트윈은 target_domain에만 있어 독립 검색어가 아니다.

개선: DOI·arXiv ID·S2 ID·OpenAlex ID를 별도 식별자 관계로 저장한다. 저널명 문자열 대신 ISSN/소스 ID를 등록하고 해당 출처를 독립적으로 순회한다. 누락된 초록은 ‘관련 없음’이 아니라 ‘판단 자료 부족’으로 보존한다.

### 9. 무인 운영의 실패 신호와 실행 시간 계약이 약하다

`scan_all_profiles`는 개별 실패를 결과 dict로 담고 CLI는 정상 반환한다. 셸도 Python 종료코드를 로그에만 쓰고 최종 `exit "$status"`를 하지 않는다. 두 검색 소스가 실패하면 메일을 보내지 않는 설계다. 40분 예산은 논문을 시작하기 전에만 확인하고, 검색·주간 분석·한 편 내부 재시도까지 포함한 절대 마감은 아니다.

개선: 부분 성공/전부 실패/발송 실패를 구조화하고 최종 종료코드와 운영 알림에 반영한다. 모든 소스 실패를 ‘논문 없음’으로 쓰지 말고 ‘오늘 수집 실패’로 알린다. 정해진 마감에는 확보된 메타데이터·초록으로 발송하고 상세 처리는 이어간다. 호스트가 꺼진 경우 프로세스 자체가 알림을 보낼 수 없으므로 실제 상시 가동 환경이 필요하다. 프로필별 schedule_frequency/time을 쓰려면 현재 전체 일괄 실행과의 연결도 구현해야 한다.

## 저널 원문 문제에 대한 설계

원문 비공개는 상세 검토의 제약이다. 그 논문의 존재, 주제, 저자 주장, 발표 정보를 알리는 기능까지 포기할 이유는 아니다.

| 확보 자료 | 제공할 내용 | 제한 |
|---|---|---|
| 본문 | 방법·실험 조건·수치·한계와 근거 문장 | 저자 주장과 독립 검증을 구분 |
| 초록 | 무엇을 다루는지, 어떤 접근인지, 저자가 주장하는 결과 | ‘초록 기반’ 표기, 본문에만 있을 결과·한계 추정 금지 |
| 제목·서지 | 신규 발표 알림, 출처, 관련될 가능성, 원문 링크 | 성과 요약과 흐름의 실질적 근거로 사용하지 않음 |

수집 경로는 다음처럼 구성한다.

1. **저널 신간 관측:** Crossref의 `/journals/{issn}/works`를 사용한다. 등록/수정 시각 기반으로 신규·갱신 메타데이터를 가져오고 온라인 발표일과 권호일은 별도로 저장한다. 이는 페이월 본문 수집이 아니다. 초록은 제출된 경우만 있다. [Crossref API](https://www.crossref.org/documentation/retrieve-metadata/rest-api/)
2. **늦게 등록된 논문 복구:** 발표일뿐 아니라 from-index-date/until-index-date 등 공급자의 변경 시각을 사용한다. 색인 갱신은 과거 논문에도 일어나므로 ‘이번에 갱신됨’을 ‘이번에 발표됨’으로 표시하지 않는다. [날짜 필터](https://www.crossref.org/documentation/retrieve-metadata/rest-api/rest-api-filters/)
3. **무료 보강:** OpenAlex와 S2에서 초록·주제·인용 관계를 보강한다. OpenAlex 무료 계정은 결제수단 없는 무료 사용량을 제공하지만, 현재 from_created_date/from_updated_date 동기화 필터는 유료 플랜 기능이다. 무료 설계에는 그 필터를 전제로 넣지 않는다. [무료 사용 정책](https://help.openalex.org/access/pricing/), [필터 제한](https://help.openalex.org/api/filtering/)
4. **OA 원문 찾기:** DOI가 있으면 기존 PDF 링크가 없어도 Unpaywall을 조회한다. 현재는 기존 링크 수집 실패 때만 폴백하고, best_oa_location의 PDF 하나만 선택한다. OA locations의 저장소 사본·버전도 후보로 다룬다. 여러 위치가 존재할 수 있다는 뜻이지 확보 성공을 보장하는 것은 아니다. [Unpaywall 데이터 형식](https://unpaywall.org/data-format)
5. **학회 직접 관측:** CVF와 OpenReview의 공개 논문·채택 상태를 소스로 추가한다. 발표/채택/수상은 각각 확인된 필드로 기록한다. 모든 투고가 채택 논문인 것은 아니다. [CVPR 공개 저장소](https://openaccess.thecvf.com/CVPR2026), [OpenReview 조회 안내](https://docs.openreview.net/how-to-guides/data-retrieval-and-modification/how-to-get-all-notes-for-submissions-reviews-rebuttals-etc)
6. **지정 학회/국내 저널:** ‘전기학회’라는 검색어 대신 정확한 간행물명과 ISSN, 공식 목차 URL을 등록한다. Crossref 누락 여부를 공식 목차와 대조하고 부족한 간행물만 공식 피드/목차 어댑터를 추가한다. 선택한 간행물별 공개 범위와 자동 접근 가능성은 별도 확인이 필요하다.

‘임팩트 높은 논문’은 한 숫자로 확정하지 않는다. 팀 관련성, 검증 가능한 수상·발표 유형, 동일 분야·비슷한 발표 연령에서의 인용 변화 등을 분리 표시한다. 저널의 명성이나 신간 인용수 0을 논문 품질 판정으로 사용하지 않는다.

## 필요한 최소 데이터 구조

기존 상세 자료 테이블은 유지하면서 다음 관계를 추가하거나 기존 스키마를 이에 맞게 확장한다.

| 관계 | 핵심 정보 |
|---|---|
| 논문 메타데이터와 식별자 | 내부 paper_id, DOI/arXiv/외부 ID, 제목·초록·출처, 초록 출처·확인일, 온라인/권호/최초공개 날짜와 정밀도 |
| 프로필별 관측 | profile_id, paper_id, source/query/config_version, first_seen, last_seen, 매칭 근거, 제외 이유, 관련성 미확정 여부 |
| 검색 작업 상태 | source/query/window, 공급자 페이지 커서, expected/received, failed/truncated, 오류 유형, 재시도 예정 |
| 분석 결과 | abstract/full_text, 생성 시각·엔진·입력 해시, 실제 처리 범위, 근거 문장 ID |
| 다이제스트와 배달 | digest_id, profile_id, 논문 ID 목록, 고정된 plain/HTML, pending/sent/failed, 시도 시각 |
| 동향 근거 | topic_id, 기간·소스 범위·설정 버전, 근거 paper_id, 관측 사실/해석/적용 아이디어 |

검색 후보 저장은 선택 이전에 한다. 제외 후보도 감사 가능한 메타데이터로 남긴다. 수집량이 늘면 보존 기간을 정하고, 선택 논문 및 동향 근거는 더 길게 보존한다. raw 응답 전체를 영구 저장해야 하는 것은 아니다.

## 최신성과 자율성을 만드는 운영 방식

일일 실행은 고정 소스 수집, 변경 자료 기록, 관련 후보 선정, 가벼운 초록 정리, 확보된 일부 본문 분석, 아침 마감 발송으로 구성한다. 상세 요약·코드 실행의 지연이 정보 배달을 막지 않게 한다.

주간 실행은 같은 소스·검색 버전의 최근 기간과 이전 기간을 비교한다. 주제별 논문 수뿐 아니라 전체 관측량 대비 비율, 새로운 연구팀/방법, 이전 결과와 다른 조건을 제시한다. 검색 범위가 바뀐 주에는 변화를 표시하고 가능하면 과거 창도 같은 설정으로 다시 수집한다. 자료가 불완전하면 증가/감소 대신 ‘추가 관측’으로 표현한다.

검색어 확장은 제한된 실험으로 자동화할 수 있다. 다음의 일주일·편수·예산은 초기 운영 정책 예시이며 효과가 검증된 수치가 아니다.

- 팀 관심 분야와 금지 범위는 고정한다. 별칭과 좁은 전문용어 후보를 신규 논문, 지정 저널의 미선택 후보, 시드 논문의 인용 관계에서 찾는다.
- 새 키워드는 근거 논문 ID와 연결해서 작은 별도 검색 예산으로 일주일 정도 시험한다. 기존 핵심 키워드를 자동 삭제하지 않는다.
- 새롭고 관련 있는 논문을 얼마나 추가했는지, 무관한 논문과 호출량은 얼마나 늘었는지 기록한다. 중복·소진 상태 때문에 수확이 줄어든 것을 분야 소멸로 오해하지 않는다.
- 무관한 주제로 커지거나 예산을 초과하면 시험을 종료한다. 넓은 새 분야 편입과 핵심 관심사의 변경은 사람에게 보여준다.
- 사람이 매주 소수 논문에 ‘업무 관련/아이디어 참고/무관/판단 불가’를 표시한다. 이 라벨은 요약 승인/반려와 구분한다.

현재 emerging_terms는 용어 빈도 추출이다. 최신 결과에 `percentage points`, `address this gap` 같은 문구가 포함되어 있어 그대로 검색 설정에 넣기 어렵다. 또한 인용망 전방 탐색인 frontier_papers가 이미 있으므로 ‘키워드 밖 발견 경로가 전혀 없다’는 진단도 과하다. 다만 현재 그 결과는 보고서 제목 목록으로 끝나고 지속 관측 후보로 저장되지 않는다.

## 검증 지표와 첨부 피드백에 대한 정정

동향 전체의 정답을 자동 증명할 수는 없어도 구성 요소는 지금 검증할 수 있다.

| 질문 | 측정 방식 |
|---|---|
| 수집이 제대로 끝났나 | 소스·검색어별 완료율, 페이지 상한·실패 건수, 마지막 성공 구간 |
| 새 논문을 얼마나 늦게 알리나 | 발표→첫 발견, 첫 발견→SMTP 수락 시간의 분포. 날짜 정밀도·소스별로 구분 |
| 원하는 곳의 논문을 놓쳤나 | 선택한 저널 공식 목차의 관련 논문 집합과 발견 목록 대조 |
| 검색어가 관련 논문을 잡나 | 시드·서베이·직접 관측 소스의 사람 확인 표본으로 검색 발견과 랭킹 선정을 따로 평가 |
| 메일이 유용한가 | precision@k, ‘아이디어 참고’ 비율, 분야별 빈칸, 사람 검토 부담 |
| 서술의 근거가 있나 | 모든 근거 ID 존재·링크·증거 구절 여부는 자동 검사, 주장과 근거의 의미적 일치는 표본 검토 |
| 전문을 실제 읽었나 | 성공한 청크·문장 범위와 누락 위치. 수치 일치율과 별도 기록 |

첨부 글의 ‘요약 검증은 선별 품질 검증이 아니다’와 ‘사람 라벨이 필요하다’는 지적에 동의한다. 다음 주장은 수정해야 한다.

- `quantization`이 가장 많이 검색됐는데 주요 목록에 없다는 사실 자체는 모순이 아니다. 관측 빈도와 개인화 추천은 목적이 다르다. 둘의 모집단과 선정 이유를 표시해야 한다.
- `venue` 입력만으로 특정 저널 구독이 구현되지는 않는다. 발견과 가점은 다른 기능이다. 현재 DB에는 venue/citation_count가 보존되지 않아 기존 저장 논문의 채움 비율을 바로 측정할 수도 없다.
- 검색된 뒤 제외된 후보를 분석하는 것은 유용하지만, 애초 검색 결과에 없는 논문의 사각지대를 닫지는 못한다. 지정 출처나 독립 시드 등 별도 경로가 필요하다.
- 서베이 참고문헌 중 키워드 0점이 아닌 비율은 그 표본에서의 매칭률이다. 분야 전체 검색 재현율의 하한이라고 일반화할 수 없다. 시간 범위·데이터 공급자에의 존재·발견·선정 단계를 나누어 평가해야 한다.
- 인용수 백테스트는 ‘우리에게 필요한 논문’의 정답이 아니다. 당시 존재한 정보만 사용하고 분야·연령을 맞춰야 한다. 작은 표본에서 차이가 유의하지 않다는 결과는 예측력이 없다는 증명이 아니므로, 음성 결과를 더 믿으라는 단정도 피해야 한다.
- ‘이 표본으로는 알 수 없다’는 한 문장은 적절한 유보다. 그 문장이 나머지 서술까지 신뢰할 수 있게 만드는 증거는 아니다.
- 정규식·숫자 세기로 구현했다고 정책이 객관적으로 옳거나 위조 불가능해지는 것은 아니다. 키워드 가중치·자리 비율은 평가할 추천 정책이고, 문구 포함 여부는 의미적 사실성 검증이 아니다.

## 구현 순서와 완료 기준

1. **관측·배달 상태 정정:** S2 부분 실패/상한 처리, 소스별 커서, 소비와 발송 분리, 주간 HTML 누락, 실제 청크 커버리지부터 수정한다. 완료 기준은 이 사례들의 회귀 테스트와 기존 테스트 통과다.
2. **후보 메타데이터 보존:** DOI/외부 ID, 초록과 출처, 날짜, 제외 이유, 프로필 관계를 저장한다. 완료 기준은 같은 후보 집합으로 재채점·누락 원인 분석이 가능하고 원문 없는 저널도 남는 것이다.
3. **지정 저널·학회 관측:** 우선순위 간행물 소수와 학회 한두 곳을 추가한다. 완료 기준은 공식 목차와 표본 대조해 누락 및 초록 확보 여부를 설명할 수 있는 것이다. 임의의 재현율 목표를 달성했다고 선언하지 않는다.
4. **메일을 발견 중심으로 변경:** 핵심 발견 3~5개와 근거 링크, 관련 저널 신간, 선택한 심층 읽기를 구성한다. 이는 초기 편집안이다. 주요 자리는 PDF 유무만으로 정하지 않는다.
5. **비교 가능한 주간 동향:** 동일 소스·기간·설정 기준의 통계, 이전 보고와의 차이, 근거 논문 연결을 구현한다. 데이터가 부족할 때는 정해진 갈래 수를 억지로 채우지 않는다.
6. **제한된 자동 검색 확장:** 근거가 있는 별칭을 시험하고 수확/잡음/사용량과 사람 라벨로 평가한다. 그 결과를 본 뒤 가중치 변경이나 더 넓은 자율화를 결정한다.

새 LLM 공급자, 유료 원문 수집, 자체 모델 학습, 복잡한 에이전트 협업부터 도입하지 않는다. 이미 있는 코드의 관측 자료와 상태 계약을 정비하는 것이 사용자가 원하는 ‘놓치지 않고 아침마다 알려주는 도구’에 직접 연결된다.
