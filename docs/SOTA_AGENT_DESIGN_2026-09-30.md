Pythonの検証は次の順序です。

1. **出典を直接取得**：モデルが返した引用文や検索スニペットを根拠本体にしない。arXiv HTML、出版社本文、コミット固定のREADMEなどをPythonが取得する。
2. **身元と版を確認**：論文ID・タイトル・版・モデル名を対応付ける。転載された同じ結果を独立した裏付けとして数えない。
3. **値の帰属を確認**：数値トークン、単位、ベンチマーク、モデル行、指標列を照合する。詳細はQ2。
4. **比較キーを照合**：トラック・用途・データセット＋版・分割・指標＋方向・学習方式／追加データ／アンサンブル等の評価プロトコル・モデル範囲・基準日がすべて合う場合だけ大小を比較する。**一つでも相違・不明なら `incomparable`。`null == null` を一致としない。**
5. **基準日をPythonが設定**：同じ基準日時点で公開済みの版だけを使う。アクセス日と公開日・更新日は別に保存する。
6. **出典URL・位置・取得日時・内容ハッシュを保存**：検索範囲も残し、「確認した候補内」と範囲を限定する。

근거 등급은 기존 A~E를 유지합니다. 공식 표라는 이름만으로 A를 주지 않고, 버전·분할·갱신일과 운영 주체를 확인합니다. 저자 결과표는 C, 주장 문장만이면 D, 검색 스니펫은 E로 후보 발견에만 씁니다. [계획서:178](/home/mjh/paper-harness/docs/AGENT_PLAN_2026-09-14.md:178)

**구체 설계**

③에서 HTML의 표 구조를 우선 보존하고, ④에서 **웹검색을 끈 읽기 전용 Codex**가 해당 표·주변 설명·S번호를 받아 추출합니다. Q1 조사 결과도 같은 추출 계약을 사용합니다. ⑤ Python 검증 이후 ⑧에 저장하고 ⑨에 표시합니다.

```text
ExtractionProposal {
  schema_version: "1",
  source_id: string,
  source_hash: string,
  claim: ResultCandidate,
  comparators: ResultCandidate[],
  unresolved: string[]

ResultCandidate {
  model_name: string,
  benchmark: string | null,
  dataset_version: string | null,
  split: string | null,
  metric: string | null,
  direction: "higher" | "lower" | null,
  value_raw: string | null,
  unit: string | null,

  model_scope: string | null,

    field: string,
    sentence_ids: integer[],
    table_id: string | null,
    row_id: string | null,
    column_path: string[],
    quote: string
  }]
}
```

출처 ID·해시·표/행 ID는 **Python이 먼저 부여한 목록에서만 선택**하게 합니다. 외부 문서마다 S번호가 반복될 수 있으므로 근거는 항상 `source_id + hash + S번호`로 식별합니다.

Python은 다음을 결정적으로 검증합니다.

- 스키마, 허용된 출처·문장·셀 ID, 원문 해시와 인용 일치.
- 숫자의 전체 토큰·부호·소수·단위 일치. `%`와 비율 변환은 명시된 규칙으로만 수행.
- 표의 `rowspan/colspan`을 복원한 뒤 **모델 행 × 지표·shot·fold·데이터셋 열의 교차 셀**과 값 일치.
- 주장값과 비교값 각각의 출처 및 조건 확인. 저자가 재실험한 baseline과 경쟁 논문의 원래 보고값을 분리.
- 향상 폭은 Python이 계산. 절대값 차이, `%p`, 상대 개선율을 구분하며 방향까지 검사.
- 비교키가 불완전하면 수치 귀속 확인과 비교 가능 판정을 분리.

문장만 있는 경우에도 단순 동시 등장으로 칸을 채우지 않습니다. **명확한 관계를 검증할 수 있는 제한된 문장 형식만 허용**하고, 애매하면 `귀속 미확인`으로 남깁니다. 일반 자연어 의미를 Python 문자열 검사만으로 완전히 증명할 수는 없습니다.

PDF 표가 깨졌다면 HTML 표나 원본 표 구조를 먼저 찾습니다. 이미지/OCR·시각 모델의 판독은 후보 생성에는 쓸 수 있지만, 행·열 대응을 독립적으로 확인하지 못하면 자동 수치 칸에는 싣지 않습니다. 두 LLM의 동의도 구조 검증을 대체하지 못합니다.

**시간·실패·표현**

- 추출은 편당 60초·1회라는 초기 상한을 제안하며, Q1 전체 300초 예산 안에 포함합니다. 실제 지연·구독 소모는 미실측입니다.
- 웹·셸·파일 접근은 끄고 공개 근거 패킷만 입력합니다. 한도·형식 오류·검증 실패 시 재호출을 늘리지 않고 기존 문장 카드로 돌아갑니다.
- 메일은 `원문 표의 값 확인 · 저자 보고`로 표시합니다. 이것을 `성능 재현 완료`나 `SOTA 검증 완료`로 바꾸지 않습니다.
- 주장값만 통과했다면 그것만 표시하고 비교값은 `확인 못함`으로 둡니다. 원문을 찾지 못한 상태를 수치 0으로 표현하지 않습니다.

**3. Q3 — 근거가 제한된 ‘읽기 관점’은 조건부로 하라**

한 줄이 **왜 이 프로필에서 읽을 만한지, 무엇과 연결되는지, 어디까지 확인됐는지**를 알려주면 유용합니다. 다만 점수·별점·추천 등급이나 “매우 뛰어난 논문” 같은 총평은 권하지 않습니다.

찬성 이유는 요지만으로 알기 어려운 읽는 목적을 전달할 수 있기 때문입니다. 반대 이유는 중복과 권위 효과입니다. 독자가 에이전트의 칭찬을 따라 반응하면, 시스템이 자기 평가를 사용자 취향으로 다시 학습할 수 있습니다.

역할을 다음처럼 나누면 중복을 줄일 수 있습니다.

| 기존/추가 요소 | 답할 질문 |
|---|---|
| **gist** | 이 논문은 무엇을 했는가? |
| **동향 서술** | 여러 논문을 함께 보면 어떤 흐름이 보이는가? |
| **추가 한 줄** | 이 프로필에서는 무엇을 살펴볼 만하며, 확인상의 한계는 무엇인가? |

현재 카드가 제목→gist→칩→근거 카드→상세 분석 순으로 만들어지는 것은 코드로 확인했습니다. 새 문장을 제목에 합치기보다는 **상세 분석 첫머리의 ‘읽기 관점’**으로 넣는 편을 권합니다. [digest.py:1985](/home/mjh/paper-harness/digest.py:1985)

**구체 설계**

⑤ 검증을 마친 뒤 ⑨ 렌더링 전, **웹검색이 꺼진 읽기 전용 Codex**에 다음만 제공합니다.

- 확정된 프로필 키워드·revision과 실제 매칭 근거.
- 검증된 논문 사실·저자 명시 한계.
- Python이 계산한 최근 동향 근거와 관측 범위.
- Q1 비교 상태 및 Q2 승인 수치.
- 기존 gist·동향 서술: 같은 내용을 반복하지 않도록 입력.

자유로운 총평 대신 다음 JSON을 제안하게 합니다.

```text
ReadingNoteProposal {
  schema_version: "1",
  paper_id: string,
  profile_revision: integer,
  relevance: {keyword_id: string, fact_ids: string[]} | null,
  trend: {
    relation: "continues" | "contrasts" | "insufficient",
    evidence_ids: string[]
  } | null,
  caveat: {
    kind: "author_limitation" | "comparison_incomplete" |
          "reproduction_unchecked",
    evidence_ids: string[]
  } | null
}
```

Python은 키워드·revision·근거 ID의 존재와 해당 논문 귀속, 비교 상태, 허용된 관계 유형을 검사하고 **검증된 짧은 문구를 고정 템플릿으로 조립**합니다. 새 수치·새 고유명사·등급을 생성할 칸은 두지 않습니다.

동향 관계의 의미까지 결정적으로 확인할 근거가 없으면 `insufficient`로 둡니다. 참조 ID가 유효하다는 것만으로 “분야가 이 방향으로 전환됐다”는 해석을 승인해서는 안 됩니다. 자유로운 장문 리뷰를 원한다면 별도의 `에이전트 해석`으로 취급해야 하며, 사실 검증 완료 표시를 붙일 수 없습니다.

예시 형식은 다음과 같습니다.

> 읽기 관점: [프로필 키워드]와 연결된 [확인된 접근]을 살펴볼 만함. [저자 명시 한계 또는 비교 미확인 상태].

‘한계’는 논문의 결함과 조사 한계를 구분합니다. **우리가 재현하지 않았다는 사실은 논문이 재현 불가능하다는 뜻이 아닙니다.** 근거 없는 칭찬뿐 아니라 근거 없는 비판도 규칙 7에 어긋납니다.

초기에는 메일당 1회·60초 상한의 묶음 처리, Q1~Q3 전체 추가 작업 300초 안에서 마지막 우선순위로 제안합니다. 여유가 없거나 구독 한도·검증 오류가 나면 한 줄을 생략하고 기존 gist·동향만 발송합니다. 추가 결제나 새 웹검색 폴백은 없습니다. 소요시간과 소모량은 미실측입니다.

**반응 신호 오염과 완화책**

오염 경로는 실제로 가능합니다.

`에이전트의 긍정 평가 → 사용자의 useful 반응 → 해당 논문 키워드 가중치 상승 → 유사 논문 노출 증가`

현재 `useful`은 0.7, `more`는 1.0으로 정의돼 있고, 반응값을 관측 키워드에 배분해 가중치에 반영합니다. **에이전트 문구가 클릭에 끼친 영향은 이 계산으로 분리되지 않습니다.** [feedback_weights.py:14](/home/mjh/paper-harness/feedback_weights.py:14), [feedback_weights.py:270](/home/mjh/paper-harness/feedback_weights.py:270)

구체적인 완화책은 다음입니다.

- **가치 평가를 줄입니다.** “추천·탁월·획기적” 대신 관련성·평가 범위·미확인 사항을 씁니다. 점수·배지·과장된 색 강조도 피합니다.
- **반응 대상을 명시합니다.** 기존 버튼 근처에 `논문에 대한 반응`을 표시합니다. 리뷰에 대한 반응을 추가한다면 별도 이벤트로 저장하고 `feedback_weights` 입력에서 제외합니다.
- **노출 상태를 기록합니다.** 발송 당시 한 줄의 유무·정확한 문구·생성 버전·근거 ID·배치 위치를 회차·수신자·논문에 연결합니다. 실제 읽었는지는 모르면 `unknown`입니다.
- **AI 평가는 학습 신호로 넣지 않습니다.** 에이전트의 추천이나 문구를 가상 좋아요로 만들거나 가중치·선정 순위에 다시 투입하지 않습니다. 사용자의 명시적 반응은 계속 1순위입니다.
- **표시 효과는 따로 관찰합니다.** 필요하면 사용자가 선택한 기간에 수신자-논문 단위로 한 줄 표시/미표시를 배정하고 순위·버튼은 동일하게 유지합니다. 소표본에서 효과를 단정하거나 임의의 ‘오염 보정계수’로 반응을 깎지 않습니다.

상세 토글 안에 넣는 것만으로 오염이 해결되지는 않습니다. 메일 클라이언트별 접힘 동작을 이번에 실측하지 않았고, 접힌 내용을 읽은 뒤에도 반응할 수 있기 때문입니다.
