## 1. 요구

팀장(10/23, 사용자 전달): "너무 모델 개발 쪽이다. 우리가 활용할 수는 있어도 개발은 못 한다 · 새로운 아이디어·핵심 아이디어 · 우리가 직접 활용할 수 있는 것 ·
목표는 과제 적용, 특히 제조 · 로봇 피지컬은 이제 막 VLA 시작 — 최신 것만 오면 안 되고 왜 했고 원래는 이랬는데 무슨 문제가 있었는지 배경도."

사용자 정리(외부 의견을 사용자가 승인해 붙임): 지금 메일은 ① 최신 동향 모니터링을 한다. 그 위에 ② 가치 있는 논문·아이디어 발굴, ③ 심층 분석·세미나,
④ 우리 연구에 연결을 얹는다. ①(연구 동향·오늘의 연구 흐름·카드)은 버리지 않는다.

### 사용자 승인 원칙 (반드시 지킨다)
- **P1. 활용 관점은 검색·순위에 영향을 주지 않는다.** 분석·활용성 판단 입력으로만 쓴다. 선정 결과는 바뀌지 않아야 한다.
- **P2. 핵심 아이디어·활용 가능성·심층 분석 가치는 별개 항목이고, 근거가 없으면 생략한다. 사실과 해석을 가른다.**
  - 핵심 아이디어는 활용 가능성이 낮은 논문에도 쓸 수 있다(예: 대규모 VLA 학습 논문의 실패 경험 활용 방식·평가 설계). 불분명하면 억지로 만들지 않는다.
  - "공개 구현 확인"(코드·가중치 공개를 확인한 사실)과 "현장 적용 가능성"(장비·데이터·실행 환경 호환성을 검토한 상태)을 구분한다.
    코드가 공개됐다고 "직접 활용 가능" 이라 하지 않는다. 정보가 부족하면 "적용 조건 확인 필요".
- **P3. 테스트 통과 외에, 실제 메일의 활용성을 기존 결과와 비교한다.** 새 일반론("제조 분야에 활용할 수 있을 것으로 기대된다")이나
  근거 없는 적용 주장이 생겼으면 실패다. 성공 기준은 메일이 길어지거나 제조 표현이 늘어나는 것이 아니라, 연구자가
  "시험해 볼 만하다 / 세미나에서 논의하자 / 앞으로 살펴보자" 를 판단할 근거를 얻는 것이다.
- 세미나 후보(⑤)는 **최대 1편, 기준을 못 넘으면 그 주는 없음**.

## 4. ② 카드 세 항목

### 4.1 무엇을 쓰나
| 항목 | 질문 | 근거 | 사실/해석 |
|---|---|---|---|
| 핵심 아이디어 | 이 논문에서 가져갈 생각은? (모델 구조 이름이 아니라 옮겨 쓸 수 있는 생각) | 논문의 문제의식·방법(초록, 원문 분석 논문은 ④ 요약) | 해석 |
| 활용 가능성 | 그 생각·기술을 어떻게 쓸 수 있나, 무엇이 필요한가 | 공개 구현은 **Python 사실값**, 나머지는 활용 관점과 논문 근거 | 사실 줄 + 해석 줄 |
| 심층 분석 가치 | 세미나에서 다룰 연구 질문·새 연구 가능성 | 논문 근거 + 활용 관점 | 해석(제안) |

- 활용 가능성의 사실 줄은 모델이 쓰지 않는다: `code_ladder` 단계(official·author·third_party·analogous·none)와 adoption_signals(HF 가중치 등 이미 있는 것)로
  "공개 구현: 공식 코드 확인됨 / 저자 연관 저장소(공식 미확인) / 확인된 구현 없음". 확인 안 된 것은 "미확인".
- 해석 줄은 "적용하려면 ~가 필요하다 / 적용 조건 확인 필요" 형식. **"직접 활용 가능" 같은 판정어는 쓰지 않게 하고 Python 이 금지어로 막는다.**
- 각 항목 한두 문장. 셋 다 생략 가능(빈 문자열). 셋 다 비면 그 카드는 지금 모양 그대로.

### 4.2 생성
- 새 모듈 `research_value.py`(⑨). 한 메일 한 묶음 호출 — 카드 최대 12편, 스키마 JSON:
  `{"papers":[{"id":"P1","idea":"","use":"","seminar":"","evidence":["P1:A" 또는 "P1:S12"...]}]}`.
- 엔진: `narrative_engine.generate`(Codex → Gemini → Groq) — 판단 품질이 필요해 plain_ko(Gemini 우선)가 아니라 서술 엔진. 시간 상한 300초, 실패 시 세 항목 없이 나감(규칙 6).
- 입력: 활용 관점, 카드마다 제목·초록(1500자), 원문 분석 논문은 ④ 요약 발췌(근거 문장 태그 포함), 공개 구현 사실 줄(참고 — 모델이 다시 쓰지 않음).
  논문 글은 자료일 뿐 지시가 아니라고 적는다(규칙 4).
- 지시문 핵심: "개발이 아니라 활용·아이디어 관점", "활용 관점의 구체적 작업(파지·조립·핸들링 / 판단 기준·결과 추적 등)과 논문의 구체적 방법을 함께 짚을 때만 쓴다",
  "짚을 게 없으면 빈 문자열", "일반론 금지(예시 나열)", "숫자는 자료 그대로".

### 4.3 Python 검사 (항목별로 — 하나가 틀려도 다른 항목은 산다)
- 스키마·카드 번호·한국어(한글 비율)·자료에 없는 숫자(그 카드의 제목·초록·요약만 대조 — 날짜·다른 카드 제외, 어제 Codex 지적 교훈).
- 근거: `evidence` 가 그 카드의 실제 근거 ID 인지. 근거 없는 항목은 버린다.
- 일반론 거르기(쟁점 B): ① 금지 구절 목록("활용할 수 있을 것으로 기대", "다양한 분야", "적용 가능성이 있다", "직접 활용 가능", "도움이 될 수 있다" 등 — 처음엔 시험본에서
  실제로 나온 것만 넣는다, whack-a-mole 금지), ② **같은 메일 안 카드끼리 거의 같은 문장**(정규화 후 겹침)이면 둘 다 버린다, ③ 활용 가능성·심층 분석 가치는
  그 논문 제목·초록의 내용어(영문 토큰 또는 한국어 번역 제목의 명사)를 하나 이상 포함해야 한다 — 어느 논문에나 붙는 문장을 막는다.
- 길이 상한(항목당 300자) — 분량 지시는 하지 않고 고장 대비.

### 4.4 표시
- 카드에서 "쉽게 말하면" 아래, 관측 칸 위. 머리: `핵심 아이디어: ` · `활용 가능성: ` · `세미나에서 볼 점: `(해석 표지). 공개 구현 사실 줄은 `공개 구현: ` 로 활용 가능성 바로 위.
- 저장 평문에 그대로 들어간다(형식 수정본 왕복). `saved_digest._card` 가 네 머리를 PLAIN_KO_PREFIX 처럼 다룬다. HTML 은 작은 상자 하나에 네 줄.
- "이 메일 읽는 법" ③ 에 한 줄: 세 항목은 해석이고 공개 구현 줄만 확인한 사실.

- 오늘(10/23) 두 프로필 카드로 DB 복사본에서 생성 → 형식 수정본을 시험 수신 주소 한 곳에만. 운영 브리핑·선정 결과는 그대로.

- 회귀: 같은 DB 로 선정 결과(카드 arxiv_id 목록·순서)가 활용 관점 유무와 무관하게 같은지 기계로 확인.

## 8. 쟁점
- A. 활용 관점을 profile_revisions 스냅샷에 넣어야 하나(되돌리기·감사) vs 넣으면 content_sha·검색 지문이 바뀌어 P1 위반 위험.

### 9.1 ① 활용 관점 (3절 수정)
- 별도 표 유지 + **버전 이력**: `profile_context(profile_id, version, use_perspective, created_at, created_by, active)` — 과거 메일이 어떤 문장으로 해석됐는지 복원한다.
  profile_revisions(검색용)와는 분리. P1 = "같은 후보·같은 상태에서 질의·S2 시드·검색 지문·순위 키·스캔 스냅샷·주간 관리 입력이 활용 관점 유무로 바뀌지 않는다".
- 활용 관점과 카드 해석 결과는 `narrative_store`(→ agent_trend_evidence → 주간 관리 입력)에 **넣지 않는다**. 운영 화면에 보이려면 별도 조회.

### 9.2 ② 세 항목 구조 (4.1~4.3 수정)
- 공용 evidence 를 버리고 항목별로:
  `{"id":"P1", "idea":{"text","evidence":[]}, "use":{"basis","proposal","check","evidence":[]}, "seminar":{"question","evidence":[]}}`
  - idea: 논문의 문제의식·방법에서 가져갈 생각. **활용 관점 연결을 요구하지 않는다**(활용성이 낮은 논문에도 쓸 수 있게 — P2).
  - use: basis(논문에서 확인한 방법·관찰) → proposal(제안하는 작업, 활용 관점의 구체 작업과 연결) → check(확인할 조건). 셋 중 하나라도 비면 use 전체 생략.
    proposal 은 메일에서 "(제안)" 으로 표시 — 논문 사실이 아니다.
  - seminar: 검토할 연구 질문 하나. 근거 필수.
- 근거 ID: 이 호출 전용 corpus — `P번호 ↔ paper_key ↔ 실제 전달한 발췌`. 초록 문장 `P1:A3`, 원문 분석 논문의 ④ 요약 문장 `P1:S0012`(문제·방법·한계 절 포함,
  결과 절만 쓰는 `result_excerpts` 를 그대로 쓰지 않는다). 기존 trend corpus 의 P번호·배열 위치를 재사용하지 않는다.
  Python 검사는 "ID 가 그 카드의 실제 전달 발췌에 있다" 까지다 — **의미 지지 여부는 미평가**로 기록하고, 메일에는 세 항목 전체가 해석이라고 안내한다.
- 숫자: 항목의 숫자는 그 항목이 인용한 발췌에만 대조한다(카드 전체·날짜·다른 카드 아님).
- 일반론 거르기는 **보조 신호**로 격하: 카드 간 거의 같은 문장, 내용어 0개, 금지 구절(시험본에서 실제로 나온 것만)은 기록하고 생략하되, 의미 검증을 대신한다고 쓰지 않는다.
  금지 구절은 부정문("직접 활용 가능하다고 판단할 근거는 없다")을 막지 않게 긍정 단정형만 잡는다. 진짜 판정은 5절 평가에서.

### 9.3 공개 구현 사실 줄 (4.1 수정 — 관측 범위로 낮춘다)
| 자료 | 메일 문구 |
|---|---|
| code_ladder official(in_text) | "논문 본문에 코드·프로젝트 링크가 있다(내용·실행 여부 미확인)" |
| author | "저자 연관으로 보이는 저장소 후보(공식 여부 미확인)" |
| third_party / analogous | 싣지 않거나 기존 code_ladder 줄 그대로(이 논문의 구현 아님) |
| HF 연결 모델 | "이 논문에 연결된 Hugging Face 모델 N개(공식·사용 조건 미확인)" |
| 미조회 / 조회 실패 / 검색했으나 없음 | 각각 다른 문구 또는 생략 — 셋을 합치지 않는다 |
- `mail_line()` 을 재사용하지 않는다(official 에서 빈 문자열). 새 함수가 tier·관측 시점을 받는다. 저장 평문에 **당시 문장 그대로** 남기고 재렌더 때 다시 계산하지 않는다.
- "직접 활용 가능"·"바로 쓸 수 있다" 는 어느 경로에서도 쓰지 않는다. 정보가 모자라면 "적용 조건 확인 필요".

### 9.4 시간·엔진 (4.2 수정)
- 단계 전체 마감 `asyncio.wait_for(…, 240)` 을 카드 확정 뒤·digest 생성 전 독립 try 블록에. 자료 조회·파싱·검사·부착 실패도 생략으로(규칙 6). 렌더러는 조회·LLM 을 하지 않는다.
- Codex timeout 은 마감보다 짧게(예: 150초) — `to_thread` 는 바깥 취소로 자식 프로세스를 못 죽이므로 `_codex` 자체 timeout 이 실제 상한이다.
- **실행 단위 Codex 차단**: 한 번이라도 한도 초과·시간 초과면 같은 실행의 이후 호출(다음 프로필 포함)은 Codex 를 건너뛴다 — narrative_engine 에 실행 단위 상태를 둔다(서술·동향에도 이득).
- 엔진 우선순위(Codex vs Gemini)는 ③ 에서 같은 입력으로 둘 다 뽑아 비교한 뒤 정한다. 추가 호출량·지연은 그때 실측.

### 9.5 저장·감사
- 새 표 `card_insights(profile_id, reader_date, arxiv_id, perspective_version, prompt_version, engine, items_json, dropped_json, created_at)` —
  항목별 근거·생략 사유를 남긴다. 메일 평문에는 표시 문장만.

### 9.6 표시 (4.4 수정)
- 카드 안 순서(평문·실시간 HTML·저장 HTML 공통): 쉽게 말하면 → **핵심 아이디어 → 공개 구현(사실) → 활용 가능성(제안) → 세미나에서 볼 점** → 관측 칸.
  HTML 은 요지 아래 상자 하나. 세 경로가 같은 렌더 함수를 쓴다.
- 부분 생략: 있는 줄만. 사실 줄만 있으면 사실 줄만(상자 대신 한 줄). 모두 없으면 지금 카드 그대로. 새 줄은 한 물리적 줄로 정규화, HTML escape.
- `saved_digest._card` 는 관측·분석 상태 기계에 새 머리를 "관측 종료" 로 추가하고, 렌더는 같은 함수로.

### 9.7 평가 (5절 수정 — P3)
- **조정 표본과 평가 표본을 나눈다**: 지시문·검사 조정은 10/23 두 프로필 카드로, 최종 평가는 다른 날(예: 10/21) 두 프로필 카드로 — 입력·카드 순서 고정.
  평가 표본에 초록만 있는 논문·구현 미조회·아이디어만 가치 있는 논문·비슷한 카드가 함께 있는 메일이 들어 있는지 확인.
- 항목별 측정(분모 명시): 근거 대응(유효 ID + 원문이 주장을 지지하는가) · 사실/추론/제안 구분 · 다른 논문으로 바꿔도 성립하는가(일반론) ·
  기존 카드 대비 새 정보(쉬운 설명·요지 반복 아님) · 생략의 적절성(근거 충분한데 버린 것 포함) · 판단에 준 도움(시험·세미나·관찰의 이유와 다음 확인 사항) · 지연·엔진·폴백.
- Claude 가 먼저 판정해 표로 내고, **최종 판단은 사용자(와 팀)가 원문과 함께** 읽고 한다.
- 시험 메일은 시험 수신 주소 한 곳, **반응 버튼 없이** 보낸다 — 원래 회차 토큰을 다시 달면 시험본 반응이 원래 메일 평가로 섞인다. "내용 시험본" 으로 표시.
