`weekly_profile_changes.py:242-252`는 이전 회차도 없고 고정 창 시작 이전 snapshot도 없을 때만 최초 revision을 쓴다. 그 쿼리도 해당 profile_id의 첫 행 하나다(`206-207`). 완전한 정상 이력에서 창보다 오래된 프로필이면 `_snapshot_at`이 먼저 찾아지므로 이 폴백까지 오지 않는다. 어린 프로필은 최초 사용자 키워드가 before에도 있으므로 그것을 새 자동 추가로 세지 않는다. 신규 프로필의 실제 collect→메일 테스트가 이를 지킨다.

운영 DB 읽기 전용 확인: `team_agent`, `team_robot`, `team_vision`은 모두 9/15 생성이다. 현재 스캔 결과를 만들거나 내일 모델 적용을 실행하지는 않았다. 초기 revision 자체가 없거나 JSON이 깨진 이력의 복구까지 보장한다고 주장하지 않는다.

### 제목 재요청과 재현 라벨

- 제목은 중복 제거·길이 검사 후 최대 40개를 고른다(`title_ko.py:65-73`). 두 번째 요청은 이미 성공한 제목을 빼고 새 번호를 매긴 누락 묶음뿐이며 최대 2회 complete 호출이다(`74-82`). 무한 반복이나 성공한 제목의 반복 요청은 확인하지 못했다. 단, **실제 HTTP 호출이 최대 2회라는 뜻은 아니다.** `summarize_engine.py:424-425,443-467`의 기존 Gemini 503 재시도와 Groq 폴백이 각 complete 안에서 돈다. 실제 공급자 호출 수·소요 시간·한도 사용량은 미실측이다. 새로 발견한 부분 성공 손실은 B에 적었다.
