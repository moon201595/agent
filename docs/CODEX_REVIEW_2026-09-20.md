## 문제 없음으로 확인한 범위와 제한

- **월요일 체인**: `run_daily_scan.sh:55-62`에서 KST 월요일에 retention→agent→scan 순서다. 주간 명령의 비정상 종료는 `|| echo`로 처리하며 `set -e`도 없다. 이 새 블록 때문에 일반 실패가 일일 스캔을 건너뛰는 경로는 확인하지 못했다. 실제 Windows 절전 복귀·05:00 실행은 미실측이다. 월요일을 통째로 자서 화요일에 실행되면 월요일 블록과 보고가 생략된다. 그다음 월요일은 마지막 월요일 스캔까지 창이 늘어나므로 “스캔이 아예 없었던 한 주”와 #2의 “스캔은 있지만 보고를 못 받은 한 주”를 구분해야 한다.
- **발송 임계 경로**: `run_profile_scan.py:543-570`은 모든 프로필 스캔·발송 시도 후 별도 루프에서 진단을 수행한다. 정확히는 성공적으로 스캔 결과가 반환된 **프로필마다 한 번**이며 전체 프로필에 대해 함수가 딱 한 번 호출되는 것은 아니다. 진단은 `client=None`, `with_narrative=False`로 호출된다(`513`). 프로필당 175초는 §8-167~168의 기존 실측이며 재측정하지 않았다.
- **기간의 정상 경로**: 지난 월요일이 늦게 실행됐거나 한 주의 스캔이 완전히 빠진 경우, 가장 최근 같은 KST 요일의 스캔과 해당 스냅숏으로 이어진다. `max(고정 창, 지난 회차)`로 다시 자르지 않는다. 다만 발송 이력과의 차이(#2), 이벤트 끝 시각(#3) 때문에 모든 연속 보고의 무중복·무누락을 보장한다고 결론내릴 수 없다.
- **귀속 기본 매핑**: 현재 OPS 6종의 종류 매핑은 실제 적용 분기와 맞고, core/seed 귀속을 분리하며 대소문자 정규화를 한다. 스냅숏 비교 자체는 표기를 보존한다. 순변화를 주체별 수치로 분해하지 않는다.

## 실행 검증과 무작위 실패 조사

1. 최초 `python -m pytest ... --randomly-seed=20260920` 시도는 **수집 전 종료 코드 4**였다. 현재 `.venv`가 `--randomly-seed` 옵션을 인식하지 않는다. 플러그인을 설치하거나 의존성을 바꾸지 않았다.
2. 설치 없이 `pytest_collection_modifyitems`에서 `random.Random(20260920).shuffle(items)`를 적용한 **집중 104개는 22.61초에 전부 통과**했다. 대상은 `test_keyword_events.py`, `test_agent_maintenance.py`, `test_observations.py`, `test_weekly_profile_changes.py`, `test_title_ko.py`, `test_monday_chain.py`, `test_trend_window.py`, `test_narrative_store.py`다. 이는 순서만 섞는 검사이며 pytest-randomly의 테스트별 RNG 초기화까지 재현한 검사는 아니다.
3. 같은 수집 순서 섞기를 전체 1,171개에 적용한 실행은 첫 15개 완료 뒤 진행하지 않아 **중단(exit 130)**했다. 전체 green을 확인했다고 주장하지 않는다. 수집 순서상 다음 항목은 `test_briefing.py::test_scan_carries_grounded_material_through_both_mail_formats`였고, 해당 항목의 단독 실행에서도 대기를 확인했다.
4. 단독 실행에 15초 진단 타이머를 두고 캡처를 해제하자 스택은 `test_briefing.py:227 → asyncio.run → asyncio/runners.py:73 → loop.shutdown_default_executor` 대기였다. 30초 제한 실행도 완료되지 않았다. 추가로 **저장소를 import하지 않는 최소 예제** `asyncio.run(main())` 안에서 `await asyncio.to_thread(lambda: "thread_done")`만 실행했다. `thread_done`은 출력됐지만 실행기는 종료하지 못하고 5초 진단 타이머에서 같은 `shutdown_default_executor` 스택으로 끝났다. 따라서 이 환경에서는 저장소 코드 없이도 발생하는 종료 대기이며, 이를 내일 운영 장애나 사용자가 보고한 세 파일의 간헐적 assertion 실패 원인으로 단정하지 않는다.
5. **요청한 무작위 실패의 근본 원인은 미확인**이다. 실패 seed·정확한 nodeid·assertion 원문이 현재 자료에 없고, 이번 집중 순서 섞기에서는 재현되지 않았다. 단독 통과/무작위 실패라는 관찰만으로 코드 결함이나 전역 상태 누수를 확정하지 않았다.
6. 코드 결함 #1~#5는 임시 합성 SQLite DB와 실제 `collect`/렌더러/`validate` 함수로, #6은 두 최종 다이제스트 함수로 재현했다. 테스트 파일은 추가·수정하지 않았다. pytest 캐시는 `-p no:cacheprovider`, bytecode는 `PYTHONDONTWRITEBYTECODE=1`로 끄고, conftest의 임시 데이터 경로를 사용했다. 실행 전 `config` import에서 저장소 `.env` 경로의 존재 검사를 일시적으로 False로 처리해 실제 파일을 읽지 않았다.
